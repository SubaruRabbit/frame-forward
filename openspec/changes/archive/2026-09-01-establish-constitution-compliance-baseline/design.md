## Context

参见 `proposal.md`。仓库由 React Native APP、Java 21/Spring Boot 多模块服务端、OpenAPI 契约和本地校验脚本组成；已有业务规格均已归档并同步到主规格。宪章要求规格先行、最小变更、分层边界、TDD、自动化质量门禁和可回滚交付，而当前 OpenSpec 配置又限制单个 change 最多涉及两个服务端模块或两个 APP feature。

受影响区域仅为 `openspec/changes/establish-constitution-compliance-baseline`、`openspec/CHANGE-PLAN.md` 和新增的治理审计文档；本 change 不修改 `frame-forward-server`、`frame-forward-app`、`contracts` 或构建配置。

## Goals / Non-Goals

**Goals:**

- 以条款、代码证据、风险、目标状态和验证命令构成可追溯的全仓差距矩阵。
- 将整改拆成满足 OpenSpec 粒度限制、依赖明确且可独立回滚的后续 changes。
- 定义所有后续整改共同使用的验收基线和阻断条件。

**Non-Goals:**

- 不在基线阶段修改代码、依赖、公共 API、数据库或产品行为。
- 不预先断言所有模块都违规；只记录可复现证据。
- 不以一次全量格式化或一次跨仓大提交完成治理。

## Decisions

### 1. 先证据审计，再创建整改 change

审计矩阵按“宪章条款、适用区域、现状证据、合规状态、风险等级、整改边界、验证方式”记录。采用可复现命令和文件/符号定位作为证据，不以主观代码风格判断替代规则。相比直接重构，这能保护既有行为并为 TDD 的 Red 基线提供输入。

### 2. 按风险与依赖拆分，而非按一次性全仓改造

后续 change 依次覆盖：质量门禁基础设施、后端模块边界、后端分层与测试、APP Feature 分层与状态、网络/存储/安全、跨端契约及发布治理。每个 change 仍须遵守最多两个服务端模块或两个 APP feature、3–7 个任务的限制；发现第二主能力时继续拆分。替代方案“一项大 change”因不可审查、难回滚且违反本仓 OpenSpec 规则而放弃。

### 3. 默认采用核心系统质量等级

仓库处理账号、认证、私有照片与删除流程，基线按核心系统阈值评估：行覆盖率不低于 90%、分支覆盖率不低于 80%、重复率不高于 2%、方法圈复杂度不高于 8。若技术负责人书面确认某独立区域属于一般系统，可在对应后续 change 中记录范围和依据；安全、隐私与数据正确性红线不降级。

### 4. 基线区分存量债务与新增违规

全量结果用于治理排序；每个后续 change 必须保证其新增/修改代码达到适用门禁，并不得扩大存量违规。只有实际整改 change 完成后才消除对应差距，不能通过扩大忽略、关闭检查或删除断言标记为合规。

### 5. 外部行为保持不变

重构 change 以现有 PRD、主规格和 OpenAPI 为行为基线。若整改需要改变 API、业务规则、数据结构、权限或 SDK 行为，必须另建行为 change，先更新 delta spec、兼容策略和迁移/回滚方案。

## Risks / Trade-offs

- [全仓审计可能产生过多整改项] → 按红线、数据正确性、架构、测试、可维护性排序，并拆为可独立验收的 changes。
- [静态搜索产生误报或漏报] → 关键结论同时使用构建结果、测试、依赖分析和人工代码审查交叉验证。
- [存量测试不足导致重构回归] → 后续 change 先补特征/架构测试形成 Red，再做最小迁移。
- [严格核心系统阈值增加治理成本] → 优先保护账号和私有数据；任何等级调整必须显式记录且不得降低红线。
- [后续改造期间宪章变化] → 每个 change 开始前重新读取宪章并复核差距矩阵与验收标准。

## Migration Plan

1. 生成只读审计证据和合规矩阵，不改变运行时状态。
2. 将整改项按依赖和风险写入 change 计划，每项关联条款及验收命令。
3. 逐个 propose、评审、apply、验证和 archive 后续 change；格式化与业务迁移分开提交。
4. 每完成一个 change 更新矩阵状态；失败时仅回滚该 change，不改写共享历史。

本基线本身只含文档，可通过撤销对应文档变更回滚；任何代码迁移的回滚方案由其独立 change 定义。
