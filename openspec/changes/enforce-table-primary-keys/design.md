## Context

`lesson_progress` 已以 `(account_id, content_version_id, lesson_id)` 建立复合主键，因此数据库层面并不存在无主键的表。MyBatis-Plus 不支持将复合主键作为 `@TableId`，使实体初始化产生告警，且不能安全使用按 ID 的框架方法。

受影响项目为 `frame-forward-server`：`bootstrap` 模块负责数据库迁移和迁移集成测试，`course` 模块负责进度实体映射。

## Goals / Non-Goals

**Goals:**

- 为课程进度提供框架可识别的单列实体主键。
- 保持原三列组合的业务唯一性和全部存量数据。
- 让应用启动时不再为该实体输出无主键告警。

**Non-Goals:**

- 不修改课程进度 API、业务流程或其他已有主键表。
- 不追溯重写历史迁移文件。

## Decisions

### 使用代理主键并保留复合唯一约束

新增不可变 `id` 列为 `lesson_progress` 的主键；将现有复合主键替换为 `(account_id, content_version_id, lesson_id)` 唯一约束。代理主键让 ORM 获得稳定实体标识，唯一约束仍由数据库保护业务幂等。

替代方案是维持复合主键并忽略 MyBatis-Plus 告警。该方案无法满足框架实体主键要求，并保留误用 `xxById` 方法的风险，故不采用。

### 通过新版本 Flyway 迁移升级存量表

新增迁移先为既有行填充 UUID，再将 `id` 设为非空主键，同时保留原组合唯一索引。历史迁移为已应用版本，不能修改。

替代方案是重建表并拷贝数据。该方案增加停机和外键处理风险，故不采用。

### 实体以单列主键映射

`LessonProgressEntity` 显式将新 `id` 字段映射为主键，其他字段继续作为普通列参与现有查询和插入逻辑。

## Risks / Trade-offs

- [给存量记录生成 ID 时发生碰撞] → 使用 UUID 并在迁移测试中验证主键唯一性。
- [迁移期间原业务唯一性短暂失效] → 在删除复合主键与创建唯一约束的相邻语句中完成，并由事务性 DDL 能力和迁移测试保障。
- [历史查询依赖复合主键] → 现有业务字段与唯一性不变；补充持久化与迁移回归测试。

## Migration Plan

1. 在开发数据库备份后执行新增 Flyway 迁移。
2. 验证所有既有记录都有唯一 `id`，且原业务组合仍唯一。
3. 部署新实体映射并启动应用，确认不再出现该实体的 MyBatis-Plus 主键告警。
4. 回滚时恢复数据库备份；Flyway 生产迁移不执行破坏性自动回滚。
