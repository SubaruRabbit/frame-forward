# Java + Spring Boot 后端开发宪章

> 适用范围：所有 Java / Spring Boot 后端项目，包括单体应用、模块化单体和微服务。
>
> 优先级：本宪章高于团队习惯、局部文档和个人偏好。任何违反本宪章的实现，都视为未完成。
>
> 目标：让后端开发在同一套规则下完成规格、实现、验证、发布与治理，确保代码可维护、可演进、可审查、可回滚。
>
> 版本：v2.0.0 ｜ 生效日期：2026-09-02 ｜ 变更记录：见 [constitution.md](../../constitution.md)「变更记录」。

## 1. 核心原则

1. SDD 强制执行。
   - 任何变更先有规格，再有实现。
   - 规格必须说明目标、范围、非目标、验收标准、风险与回滚思路。
   - 需求变更先更新规格，再修改代码。
   - 本仓库以 OpenSpec 作为规格载体（`openspec/`），涉及 openspec 变更时先更新对应 change 并通过确认，再实现。

2. TDD 强制执行。
   - 必须遵循 `Red -> Green -> Refactor`。
   - 禁止“先写实现，后补测试”作为默认做法。
   - 新增能力必须先有失败测试，再实现最小代码，再重构。

3. DRY、KISS、YAGNI 为强制决策原则。
   - 重复逻辑必须治理，不能无限复制。
   - 优先最简单、最直接、最容易维护的方案。
   - 未经批准的未来需求，不得提前实现。

4. SOLID 为默认设计约束。
   - 单一职责：类和模块只承担一个主要变化原因。
   - 开闭原则：通过抽象和组合扩展，而不是频繁修改稳定核心。
   - 里氏替换：子类不能破坏父类语义。
   - 接口隔离：接口要小而专，禁止胖接口。
   - 依赖倒置：高层策略依赖抽象，不依赖基础设施细节。

5. 代码必须可读、可测、可审查。
   - 任何让人“看不懂但能跑”的实现，默认不合格。
   - 复杂度应该被设计消化，而不是留给后来人猜。

6. 文档与注释默认使用中文。
   - 生成的 Markdown 文档内容应使用中文输出，除非有明确的外部规范要求使用其他语言。
   - 代码注释应使用中文，优先用中文解释业务意图、边界条件和设计原因。
   - 只有在必须保留英文术语、接口名、协议字段名或第三方固定标识时，才允许使用原文。

## 2. 技术基线

1. Java 基线：JDK 21。
2. 框架基线：Spring Boot 优先使用 3.5.x 系列的最新稳定版本。
3. 其余依赖的 jar 包，优先选择同级别最新稳定版本，并以兼容性和安全性为前提。
4. DAO 层操作 MySQL 时，默认使用 MyBatis Plus。
5. 测试框架：JUnit 5 为默认标准。
6. 构建工具：默认只使用 Maven。
7. 文档格式：Markdown。
8. 配置管理：环境隔离，禁止将密钥写入仓库。

## 3. 架构要求

1. 默认架构采用传统分层架构和贫血模型。
   - `Controller`：负责协议转换、参数校验和响应映射。
   - `Service`：负责业务编排、业务规则和事务边界。
   - `Business`：负责复杂业务规则、规则组合和可复用的业务判断。
   - `Manager`：负责多个业务流程的协调、跨场景编排和复合流程控制。
   - `Repository` / `DAO`：负责数据访问和持久化操作。
   - `Model` / `Entity` / `DTO`：主要承载数据，不承载复杂业务行为。

2. 业务规则主要集中在服务层和业务层。
   - Controller 不承载业务决策。
   - Model 以数据承载为主，不把复杂逻辑塞进对象方法。
   - Repository / DAO 只负责数据访问，不写业务判断。
   - 简单业务规则可以放在 `Service`，复杂业务规则可以拆到 `Business`。
   - 纯流程协调可以由 `Service` 直接调用 `Manager`，但不应把规则判断混入流程协调。

3. 分层边界必须清晰。
   - 允许的调用关系为：`Controller -> Service`、`Service -> Business`、`Service -> Manager`、`Business -> Manager`、`Manager -> Repository / DAO`。
   - 典型业务链路优先按：`Controller -> Service -> Business -> Manager -> Repository / DAO` 组织。
   - `Business -> Manager` 是强制规则，`Manager` 不得反向依赖 `Business`。
   - `Controller` 只能调用 `Service`，不直接操作数据库。
   - `Service` 可以直接调用 `Manager`，也可以先调用 `Business` 再由 `Business` 调用 `Manager`；优先让复杂规则经过 `Business`，让纯流程经过 `Manager`。
   - `Service` 不能绕过职责边界把复杂业务规则塞进自己，也不能把数据访问细节下沉到自己。
   - `Manager` 只负责流程协调和数据持久化相关的编排，不直接反向进入 `Service` 或 `Controller`。
   - `Repository / DAO` 只负责数据访问，不得反向依赖上层业务编排逻辑。
   - 基础设施包（`converter` / `gateway` / `rpc` / `component`）通过接口隔离接入分层：`converter` 做纯 DTO 转换，可被 `Service` / `Business` / `Manager` 调用；`gateway` / `rpc` 做第三方或跨服务适配，可被 `Service` / `Manager` 调用；`component` 提供通用技术组件。均不得反向依赖上层业务规则。
   - 禁止循环依赖。

4. 优先组合，谨慎继承。
   - 可复用逻辑优先下沉为组件、工具类或独立服务。
   - 继承只在表达稳定的“是一个”关系时使用。

5. 单体与微服务都要遵守相同原则。
   - 单体按业务能力分包，不按技术文件夹堆砌。
   - 微服务按业务边界划分，不按组织结构切分。

## 4. 分层职责

### 4.1 Controller 层

1. 只做请求与响应的适配。
2. 负责参数校验、协议转换、状态码映射。
3. 不写事务控制、不写复杂业务规则、不直接操作持久化细节。
4. 统一处理错误映射，但不做补偿逻辑。

### 4.2 Service 层

1. 负责用例编排。
2. 负责事务边界。
3. 负责调用 Business 和 Manager，并协调外部服务和事件发布。
4. 承载基础业务规则，适合处理简单判断、参数校验后的轻量分支和单次流程控制。
5. 优先把复杂规则交给 Business，把复合流程交给 Manager。
6. 不应堆积复杂规则、跨场景判断或多步骤复合逻辑，避免变成”上帝服务”。
7. 边界判断：`Service` 对应单个用例（一次请求的业务目标）内的编排；跨用例、可被多个 `Service` / `Business` 复用的协调下沉到 `Manager`。拿不准时按「是否被多个调用方复用」判断。

### 4.3 Business 层

1. 负责复杂业务规则、规则组合和复用性较强的业务判断。
2. 适合承载需要多步计算、条件分支较多或容易膨胀的业务逻辑。
3. Business 层负责调用 Manager，不能直接访问控制器，也不直接做持久化操作。
4. Business 层应保持可测试、可复用、可被多个 Service 调用。
5. Business 层应避免承担事务边界控制和底层数据访问细节。

### 4.4 Manager 层

1. 负责多个业务步骤、多个 Service 或多个 Business 的协调。
2. 适合承载跨场景流程控制、复合事务编排和复用型协调逻辑。
3. Manager 层负责调用 Repository / DAO，不直接写 SQL、不直接处理底层持久化细节。
4. Manager 层不承载业务规则本身，只负责把流程串起来。
5. Manager 层应保持清晰边界，避免变成新的”上帝层”。
6. `Manager` 不因流程较长而接管业务规则；规则仍留在 `Service` / `Business`。

### 4.5 Model 层

1. 负责承载数据结构和基础属性。
2. Model / Entity 以字段和简单读写为主，不承担复杂业务规则。
3. Model 的职责是稳定、清晰、易传输、易持久化。

### 4.6 Infrastructure 层

1. 负责技术实现细节。
2. 包括数据库访问、缓存、消息队列、文件存储、第三方 API 适配等。
3. 所有外部依赖都应通过清晰接口隔离。
4. 基础设施失败必须向上返回可诊断的错误，不得悄悄吞掉。

## 5. 编码规范

1. 命名应以业务语义优先。
   - 类名、方法名、字段名应让业务人员也能大致看懂意图。
   - 禁止 `Manager`、`Helper`、`Util` 这类无语义泛化命名泛滥。

2. 方法应短小、单义、可测试。
   - 一个方法只做一件事。
   - 长方法要么拆分，要么提炼表达式。

3. 注释只解释“为什么”，不重复“是什么”。
   - 代码已经能表达的内容，不要再写废话注释。
   - 复杂决策、边界条件、历史兼容原因可以注释。

4. 公开 API 要稳定。
   - 对外暴露的接口、DTO、事件、错误码要尽量向后兼容。
   - 破坏性变更必须经过版本策略与迁移方案设计。

5. 代码格式由自动化工具统一。
   - 不允许在 PR 中讨论个人格式偏好。
   - 格式化只是一致性要求，不是设计替代品。
   - Java 代码必须使用 Spotless 执行格式化，格式规则必须采用 Eclipse JDT；Spotless 是构建和 CI 的唯一格式化执行入口。
   - Eclipse JDT XML 配置必须以可复现的方式纳入仓库或由构建配置固定引用，不得依赖开发者本机的个人 IDE 设置。
   - 提交 Java 代码前必须执行 `mvn spotless:apply`；验证必须执行 `mvn spotless:check`。`spotless:check` 失败时不得合并或发布。
   - Spotless 的目标范围、排除范围、导入顺序、未使用导入清理、文件末尾换行和空白字符规则必须在 Maven 配置中明确，不得通过本地参数临时改变。
   - 新增或修改的 Java 源码、测试源码都必须纳入格式化检查；生成代码、第三方复制代码等确需排除的内容必须有明确目录边界和文档说明。
   - 格式化产生的纯格式变更应与业务变更分开提交；若无法拆分，必须在变更说明中明确格式化范围及原因。
   - 服务端 reactor 的格式化范围为各模块的 `src/main/java` 和 `src/test/java`；仅排除模块 `target` 与 `generated-sources` 目录，禁止按业务包、文件名或本地参数扩大排除范围。
   - 服务端完整质量入口为 `QUALITY_BASE_REF=<Git 基线引用> mvn verify`：它在 `validate` 阶段执行 Spotless，在测试后生成 JaCoCo XML 和 PMD/CPD 报告，并由 `bootstrap` 校验变更可执行代码。该环境变量缺失、基线不可解析或报告缺失均必须失败。

## 6. 测试要求

1. 新能力必须有测试。
   - 功能测试、单元测试、集成测试按风险分配。
   - 关键业务逻辑必须覆盖正常路径、异常路径和边界条件。

2. 测试必须可重复、可隔离、可并行。
   - 禁止依赖随机性、外部时钟、共享状态和不稳定网络。
   - 有外部依赖时，要么做隔离，要么做可控测试夹具。

3. 测试优先级建议如下。
   - 业务规则：服务层单元测试优先。
   - 用例编排：服务层测试优先。
   - API 契约：接口测试优先。
   - 数据访问：集成测试优先。
   - Manager 层和 Business 层若承担复杂逻辑，必须补充针对性的单元测试。

4. 关键缺陷必须补测试。
   - Bug 修复不是只改代码，必须补回归测试。

## 7. 质量门禁

1. 以下任一失败，都不得合并或发布。
   - 构建失败。
   - 测试失败。
   - Spotless 格式检查失败。
   - 安全高危问题未处理。
   - 架构规则被破坏。
   - 评审未完成。
   - 发布检查未通过。

2. 默认质量阈值。

| 项目等级 | 行覆盖率 | 分支覆盖率 | 代码重复率 | 方法圈复杂度 | 审批要求 |
|---|---:|---:|---:|---:|---|
| 一般系统 | >= 85% | >= 75% | <= 3% | <= 10 | 至少 1 名有经验开发者 |
| 核心系统 | >= 90% | >= 80% | <= 2% | <= 8 | 至少 2 名审批者，包含模块负责人 |

3. 项目等级判定。
   - 核心系统：收入、交易、结算、合规、审计、高敏数据、强监管、强可用性要求等场景。
   - 一般系统：不满足核心系统条件，且经团队确认后归类。

4. 门禁标准不得随意降级。
   - 工具可以替换。
   - 标准不能放宽。
5. 阈值测量口径：
   - 行 / 分支覆盖率：以 JaCoCo 统计，按本次变更涉及的新增代码为准，全量结果为参考。
   - 代码重复率：以 SonarQube 或 PMD CPD 统计为准。
   - 方法圈复杂度：以 SonarQube 统计为准。
   - 无法自动测量时，须在 PR 中人工说明测量方法与结果。
   - 当前服务端以 JaCoCo XML 汇总相对 `QUALITY_BASE_REF` 的新增可执行行，行覆盖率不得低于 90%，分支覆盖率不得低于 80%；没有新增可执行行时必须输出明确的跳过结果。PMD CPD 以重复行占全部生产 Java 源码行的比例计算，不得超过 2%；PMD 圈复杂度超过 8 即阻断构建。

## 8. 数据与一致性

1. 单体优先本地事务。
2. 微服务优先最终一致性。
3. 不把分布式事务当作默认方案。
4. 关键写操作必须考虑幂等、去重与重复提交。
5. 数据模型要服务业务，不要让表结构反向绑架业务设计。

## 9. 异常处理

1. 异常分层要清楚。
   - 业务异常：业务规则不满足。
   - 服务异常：用例编排失败。
   - 基础设施异常：数据库、网络、第三方服务等失败。

2. 业务异常和服务异常都应带有明确的上下文信息，便于定位问题。

3. 不得吞异常。
   - 不能只记录日志然后继续假装成功。
   - 不能把根因全部包装成无意义的统一异常。

4. 对外错误信息要可诊断，但必须脱敏。
   - 不能暴露密钥、内部路径、SQL 细节、用户隐私和系统敏感信息。

## 10. 安全与配置

1. 密钥严禁入库。
2. 配置必须支持环境区分。
3. 生产权限采用最小权限原则。
4. 任何第三方接入都要评估超时、重试、限流、熔断和降级策略。
5. 外部输入一律不可信，必须校验、转换和约束。

## 11. 可观测性

1. 每个服务都应具备结构化日志。
2. 请求链路必须有可追踪标识。
3. 核心业务指标要能被监控。
4. 关键操作要可审计。
5. 线上故障必须能快速定位到“哪一步、谁触发、失败在哪、影响多大”。

## 12. 发布与回滚

1. 每次发布都必须有明确的变更摘要。
2. 每次发布都必须有验证方式。
3. 每次发布都必须有回滚预案。
4. 核心系统发布前应补充影响评估与回滚验证记录。
5. 不允许“先上线再补文档、再补验证”。

## 13. 评审要求

每个 PR 至少回答以下问题：

1. 改了什么。
2. 为什么改。
3. 怎么验证。
4. 有什么风险。
5. 如果出问题怎么回滚。

评审关注点优先级如下：

1. 业务正确性。
2. 边界条件。
3. 可维护性。
4. 安全性。
5. 性能与扩展性。

## 14. 完成定义

一个变更只有同时满足以下条件，才算真正完成：

1. 规格已更新并通过确认。
2. 相关测试已编写并通过。
3. 质量门禁满足对应等级。
4. 架构边界没有被破坏。
5. 评审意见已闭环。
6. 发布与回滚方案已经准备好。

## 15. 治理原则

1. 宪章是强制约束，不是建议清单。
2. 所有例外都必须显式记录并由负责人批准。
3. 任何团队惯例都不能高于本宪章。
4. 宪章本身可以演进，但必须经过评审、版本化和生效声明。
5. 例外审批与记录：
   - 一般系统：例外由模块负责人审批。
   - 核心系统：例外由模块负责人与架构负责人共同审批。
   - 所有例外记录到 `docs/constitution/exceptions.md`，写明范围、原因、风险、回滚方式、审批人、日期。
