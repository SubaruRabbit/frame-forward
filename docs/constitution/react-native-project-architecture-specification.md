## 1. 总则

### 1.1 目的

统一代码归属和依赖边界，使开发者能够快速定位代码、控制模块耦合，并通过显式注册点新增或移除功能。

目录服务于职责划分，不以目录数量衡量架构质量。未使用的目录不需要创建。

代码与配置示例集中在[实践示例附录](./react-native-architecture-examples.md)。示例用于说明本规范的落地方式，不增加工具安装要求；适用版本、可运行范围和省略内容见附录说明。

### 1.2 适用范围与技术前提

- 本规范的默认方案为 React Native CLI、TypeScript 和 React Navigation；服务端数据推荐使用 TanStack Query，共享客户端状态可按需使用 Zustand，不强制同时引入，具体规则见 §4.7。
- 使用 Expo 或其他导航、状态管理方案时，应当提供项目级适配说明，替换不适用的工程配置，并保留模块边界原则。
- RN、Node、TypeScript、导航库、已采用的状态与查询库及包管理器版本必须在项目配置或工程说明中明确，提交所用包管理器的锁文件。配置示例须与项目实际版本核对，不能覆盖现有必要配置。
- 既有项目可以分阶段迁移；迁移清单应当列出旧目录、目标归属、负责人和完成条件。新增代码遵循本规范，遗留例外单独记录。

### 1.3 强制等级

| 等级             | 含义                       | 评审要求               |
| ---------------- | -------------------------- | ---------------------- |
| 必须（MUST）     | 规范适用范围内必须遵守     | 不满足不得合入         |
| 应当（SHOULD）   | 默认遵守，允许有依据的偏离 | 在 PR 中说明原因与影响 |
| 可以（MAY）      | 按需要选择                 | 不强制                 |
| 禁止（MUST NOT） | 规范适用范围内不允许       | 出现则不得合入         |

项目级适配必须有明确范围和评审记录，不能以临时注释绕过强制规则。

### 1.4 架构总览

采用「应用装配 + Feature 内聚 + 共享业务 + 通用能力 + 基础设施」结构。

| 区域                                        | 职责                                              |
| ------------------------------------------- | ------------------------------------------------- |
| `app/`                                      | 启动、Provider、导航和初始化装配，连接各模块      |
| `features/`                                 | 用户可感知的业务功能，包含页面、交互与用例        |
| `domains/`                                  | 被多个 feature 使用的共享业务模型、状态与业务组件 |
| `components/`、`hooks/`、`utils/`、`theme/` | 无业务语义的通用能力                              |
| `services/`                                 | HTTP、存储、分析、推送等外部能力适配              |
| `contracts/`                                | 最小共享契约，例如路由参数和平台能力接口          |
| `config/`、`i18n/`、`assets/`               | 公共配置、国际化基础设施和公共资源                |

依赖依据 §3 的矩阵管理，不使用「所有同层禁止依赖」或「横向目录任何层都能引用」的笼统规则。类型导入同样受边界管理。

## 2. 目录结构

### 2.1 推荐目录树

下列目录表示代码归属，按需创建；示例业务模块不要求全部存在。

```text

├── android/                         # 原生宿主与 Android 构建配置
├── ios/                             # 原生宿主与 iOS 构建配置
├── src/
│   ├── app/
│   │   ├── navigation/
│   │   │   └── RootNavigator.tsx
│   │   ├── providers/
│   │   │   └── AppProviders.tsx
│   │   ├── query/                   # 采用 TanStack Query 时创建
│   │   │   ├── queryClient.ts       # 客户端创建与通用默认配置
│   │   │   └── lifecycle.ts         # 按需：连接网络、应用焦点与 Query 管理器
│   │   └── bootstrap/               # 初始化、依赖注入与后台任务装配，见 §5.4
│   ├── features/
│   │   ├── auth/
│   │   ├── order/
│   │   └── profile/
│   ├── domains/
│   │   └── session/                 # 共享登录态、用户身份模型
│   ├── components/                  # 通用 UI，无业务语义
│   │   └── Button/

│   │       ├── Button.styles.ts     # 按复杂度拆分

│   │   │   ├── client.ts            # HTTP 传输、超时、通用错误，内部实现

│   │   ├── storage/
│   │   ├── network/                 # 按需：网络状态读取与订阅适配
│   │   ├── analytics/
│   │   └── push/

│   └── assets/                      # 公共图片、字体、图标
├── __tests__/                       # 跨模块集成测试

├── .prettierrc.js
├── Gemfile
└── .gitignore
```

### 2.2 根目录与原生工程

- 新增 JS/TS 业务实现必须放在 `src/features/` 或 `src/domains/`。根目录 `App.tsx` 仅负责装配。
- `index.js` 可以进行组件注册、后台任务注册及必须早于组件挂载的初始化，不承载业务实现。
- `android/`、`ios/` 可以因 SDK 集成、权限、签名、构建配置、深链接、原生能力或 RN 升级而修改；变更必须说明用途，并验证受影响平台。
- 应当避免直接修改自动生成的原生文件；确需修改时，说明生成过程和变更保留方式。
- 环境文件的加载工具和环境选择方式由项目明确。客户端环境变量会进入可分发产物，不得用于存放服务端密钥；`.env.example` 只包含键名和安全示例。

### 2.3 平台差异实现

平台文件、统一入口及测试配置示例见[附录 A.11](./react-native-architecture-examples.md#a11)。

- 少量平台差异可以在所属模块内使用 `Platform`；复杂差异可以拆为 `Xxx.ios.ts(x)`、`Xxx.android.ts(x)`，需要与非原生运行环境区分时使用 `Xxx.native.ts(x)`。平台文件仍属于原模块，不另建跨业务的 iOS/Android JS 目录。解析机制见 [RN 平台差异代码文档](https://reactnative.dev/docs/platform-specific-code)。
- 各平台实现必须满足同一公开契约；调用方通过不含平台后缀的统一入口访问，不跨模块指定某个平台内部文件。平台专属能力应在契约中明确可用性或不支持时的结果，不能靠缺失导出让调用方猜测。
- 例如 `components/DatePicker/index.ts` 可以转导出 `./DatePicker`，由 `DatePicker.ios.tsx` 和 `DatePicker.android.tsx` 提供实现。是否提供通用回退文件由支持平台决定；必须验证每个支持平台能解析到正确实现。平台后缀不改变 §3.3 的模块边界与入口权限。
- 自定义原生能力的 JS/TS 适配归所属 `services/<adapter>/`，原生实现归 `ios/`、`android/` 或项目明确的原生包；业务模块通过适配器公开入口调用。通用 UI 的平台差异仍留在组件模块，不因使用 RN 组件而搬入 services。
- 类型检查、测试和边界检查必须覆盖支持平台的实现；运行时循环检测按各平台实际解析的依赖图执行，不将互斥平台的边简单合并后判环。具体解析配置与验证要求见 §7.4 和 §8。

## 3. 依赖边界

### 3.1 允许依赖矩阵

矩阵约束生产源码导入，包括别名、相对路径、转导出、动态导入和 `require`；未列出的依赖默认禁止。第三方包规则见 §4.5，测试源码的补充边界见 §3.4。

| 来源               | 允许引用                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------------- |
| `app/`、根入口     | 各区域的公开入口，以及 app 内部实现                                                                             |
| `features/<name>/` | 本模块；domains 公开入口；通用能力；services 公开入口；共享契约、配置、国际化和公共资源                         |
| `domains/<name>/`  | 本领域；经本节例外清单批准的其他 domain 公开入口；通用能力；services 公开入口；共享契约、配置、国际化和公共资源 |
| `components/`      | 本区域组件；hooks、utils、theme、contracts、i18n、assets                                                        |
| `hooks/`           | 本区域；utils、services、theme、contracts、config、i18n                                                         |
| `services/`        | 本区域其他适配器的公开入口；utils、contracts、config                                                            |
| `utils/`           | 本区域及不带运行时业务依赖的 contracts 类型                                                                     |
| `theme/`           | 本区域及静态 assets                                                                                             |
| `contracts/`       | 本区域；必要的第三方类型，禁止业务运行时依赖                                                                    |
| `config/`          | 本区域，不依赖业务模块                                                                                          |
| `i18n/`            | 本区域、config、utils、contracts                                                                                |
| `assets/`          | 静态资源，不依赖其他区域代码                                                                                    |

- 禁止 feature 之间直接导入或通过转导出访问彼此的实现及类型。跨模块业务流程由负责该用例的 feature 持有；app 只连接公开能力，具体方式见 §5.1。共享业务归入 domains。
- domain 之间默认禁止导入；确有稳定的单向业务依赖时，可以经评审加入项目级例外清单。清单必须记录来源模块、目标模块、允许的公开入口及导出项、类型或运行时导入范围、业务理由、负责人和评审记录，并与自动化检查配置在同一变更中更新。禁止用目录通配符放开全部 domain 依赖。
- 批准的 domain 依赖不得形成循环，包括仅由类型导入构成的领域依赖环；批准一个方向不自动批准反向依赖。未批准时，通过调用方传入最小数据或注入所需接口完成协作，不复制另一领域模型，也不经 contracts 转导出来绕过限制。
- 多个领域共享且无明确单一业务所有者的最小契约可以放入 contracts；已有所有者的业务类型保留在所属 domain。跨领域用例的顺序、失败处理及补偿决策归负责该用例的 feature。
- 禁止任何运行时循环依赖。仅换成别名或通过 barrel 转导出不能消除依赖关系。
- 通用组件应当通过 props 和回调接收业务数据，不通过通用 hook 隐藏具体业务请求。
- 模块内部可以使用相对路径；跨模块必须使用别名和公开入口。是否越界以解析后的实际路径为准，不能仅凭 `../` 的数量判断。

### 3.2 状态访问边界

- 页面临时状态由页面或组件自身维护，不为共享方便默认提升到应用级。
- 跨组件共享状态可以通过 props、回调或所属模块定义的 Context 与 hooks 提供；仅在确有需要时引入第三方状态管理工具。
- 业务 Context、Provider 和相关 hooks 放在所属 feature 或 domain；app 只负责按需要挂载 Provider，下层不得反向导入 app 获取状态。
- API 模块和 services 通过参数或注入接口获取所需数据，不直接读取业务状态容器，也不调用 React hooks。
- 采用 TanStack Query 或 Zustand 时遵守 §4.7；采用其他工具时补充项目级使用约定，保持状态归属和依赖边界。

### 3.3 公开入口

`index.ts`、`registration.ts` 与 app 装配示例见[附录 A.8](./react-native-architecture-examples.md#a8)。

模块按职责和以下路径约定划分；各区域在 §3.1 中的“本区域”允许访问同区域其他模块的公开入口，不授予访问其内部实现的权限。

| 区域                                                  | 模块粒度                                             | 默认公开入口                                                                                                       |
| ----------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `features/`、`domains/`                               | 每个直接子目录为一个模块；内部子目录不另算跨模块边界 | `@features/order`、`@domains/session` 对应模块 `index.ts`；装配入口权限另见下文                                    |
| `services/`                                           | 每个适配器直接子目录为一个模块                       | `@services/api` 对应 `services/api/index.ts`；`client.ts` 等文件为内部实现                                         |
| `components/`                                         | 每个直接子目录或单文件组件为一个模块                 | `@components/Button` 对应 `Button/index.ts` 或 `Button.tsx`                                                        |
| `hooks/`、`utils/`、`theme/`、`contracts/`、`config/` | 每个顶层能力文件或直接子目录为一个模块               | `@hooks/useDebounce`、`@theme/tokens`、`@contracts/navigation` 等单文件入口，或 `@utils/date` 对应 `date/index.ts` |
| `i18n/`                                               | 整个区域为一个模块                                   | `@i18n` 对应 `i18n/index.ts`                                                                                       |
| `assets/`                                             | 静态资源按文件寻址，不要求 barrel                    | `@assets/icons/ic-home.png` 等实际资源路径                                                                         |
| `app/`                                                | 整个区域为装配模块                                   | 根入口按需调用 `@app/bootstrap/...` 等 app 内部能力；下层生产模块仍禁止导入 app，测试访问见 §3.4                   |

- 单文件入口不强制再包装一层目录或 `index.ts`；多文件能力模块默认由其 `index.ts` 暴露最小接口。例如目录树中的 `@utils/date` 合法，外部引用 `@utils/date/formatDate` 则越界。
- 同一逻辑入口不得同时由同名文件和同名目录竞争解析；§2.3 的平台文件视为同一模块的实现变体。新增其他粒度或公开子入口时，必须在项目入口约定及边界检查配置中明确，不能仅靠新增别名使内部文件公开。
- 外部调用必须通过模块公开入口，例如 `@features/order`、`@domains/session`、`@services/storage`、`@components/Button`。
- feature 和 domain 可以提供单独的 `registration.ts` 装配入口，生产代码中仅供 app 导入 Provider、初始化入口、翻译资源等；根入口通过 app 的装配函数使用这些能力，测试访问见 §3.4。
- 禁止外部深路径引用 `@features/order/hooks/useOrder` 等内部文件。
- 模块内部直接引用内部文件，不从自己的 barrel 回导，避免循环。
- 不强制创建覆盖全部组件的 `components/index.ts`；可以使用组件级入口。若提供总入口，仍须确保无循环依赖和非必要初始化副作用。

### 3.4 测试代码边界

用例 fake 测试见[附录 A.1](./react-native-architecture-examples.md#a1)，边界配置与允许／拒绝文件见[附录 A.7](./react-native-architecture-examples.md#a7)。

测试代码必须纳入架构检查，按下表配置来源权限，不得整体排除测试目录。

| 来源                             | 允许引用与限制                                                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 模块内就近测试及私有测试辅助代码 | 可以访问本模块内部实现与本模块 `registration.ts`；访问其他生产模块时遵守被测模块的依赖矩阵与公开入口规则                |
| app 内装配测试                   | 可以访问 app 内部实现及 app 获准访问的模块入口，包括 `registration.ts`                                                  |
| 根 `__tests__/` 跨模块集成测试   | 可以访问各模块公开入口，以及项目明确指定的 app 装配入口或测试装配入口；不得直接访问业务模块内部实现或 `registration.ts` |
| 共享测试辅助代码及测试替身       | 明确放置在测试专用路径，通过公开契约提供 fixture、fake 或 mock；不得转导出生产内部实现或其他模块的私有测试辅助代码      |
| `e2e/`                           | 通过应用外部行为及测试驱动接口验证流程；可以使用测试专用辅助代码，不直接导入业务内部实现                                |

- 模块测试可以使用共享测试辅助代码；私有测试辅助代码只能由本模块测试使用。测试替身中使用 HTTP 模拟、存储模拟等测试工具不要求包装为生产 service。
- 生产源码禁止导入或转导出测试文件、fixture、mock、fake 和测试装配入口。项目必须明确这些文件的路径或命名匹配规则，避免测试权限被生产代码借用。
- `jest.mock` 等以路径指定被替换模块的调用同样遵守上述访问范围；检查器无法识别时必须在评审中检查，不能用 mock 路径绕过公开入口。

## 4. 各区域职责

### 4.1 app：应用装配

负责 Provider 组合、导航注册、启动协调和依赖注入；运行时与后台任务初始化遵守 §5.4。

可以读取最小装配状态，例如是否登录、会话恢复是否完成，以决定展示启动页、登录栈或主导航。禁止在 app 内实现登录请求、订单规则、token 刷新算法等业务逻辑；app 只调用所属模块公开能力。

app 可以选择依赖实现、传递回调、适配公开接口并管理订阅；业务操作的先后顺序、重试条件、失败分支和补偿决策必须保留在用例所属 feature 或能力所属 domain，不能写进 app 的连接回调。完整协作示例见 §5.1。

导航栈配置集中于 `app/navigation/`，可以按业务拆分多个导航文件，不要求所有路由挤在一个文件中。公共路由契约统一从 `contracts/navigation.ts` 获取，禁止页面反向导入 app 导航实现。路由参数应当使用可序列化的最小数据，例如实体 ID，不传函数、状态容器实例或完整可变实体。

### 4.2 features：业务功能

一个 feature 表达一个稳定的业务功能或用例集合，不机械地按页面拆模块。`orderDetail` 通常是 `order` 内的页面，除非具有独立的业务边界。

```text
features/order/
├── screens/
│   └── OrderDetailScreen/
│       ├── OrderDetailScreen.tsx
│       └── OrderDetailScreen.styles.ts   # 按需
├── components/
├── api/
│   └── orderApi.ts                       # 业务接口路径与 DTO 映射
├── queries/                             # 按需：query keys、查询与 mutation hooks
├── state/                               # 按需：Zustand 客户端状态
├── hooks/                               # 其他业务组合 hooks
├── useCases/                            # 按需：流程、所需接口与失败处理
├── types/
├── utils/                               # 模块私有工具
├── locales/                             # 模块文案，按需
├── assets/                              # 模块资源，按需
├── index.ts                             # 页面与经评审的公开能力/类型
└── registration.ts                      # 可选，仅供 app 装配
```

- 子目录按需创建；简单页面可以直接放在 `screens/`，复杂页面再拆成独立目录。
- 私有代码留在模块内；只有复用场景和稳定职责清晰后才抽取。
- 私有接口路径放在模块 `api/`，不集中堆放到 `services/api/endpoints.ts`。
- 对外导出应当保持最小范围，不把所有内部 hooks、actions 和工具函数全部转导出。

### 4.3 domains：共享业务

承载多个 feature 需要的业务概念，例如 session、用户身份或购物车模型。可以包含业务类型、API、状态逻辑、hooks 和业务组件，但不得依赖 feature 页面或 app 导航实现。

本规范中的 domain 指共享业务模块，不要求它是 DDD 或 Clean Architecture 中不依赖框架与基础设施的纯领域层。需要独立验证的业务规则可以在模块内部保持纯函数或纯模型；是否进一步分层由复杂度决定，不强制增加目录。

复用次数仅作为抽取信号：无业务语义的能力进入通用层；仍带业务语义的能力进入所属 domain。两个页面使用同一组件，不自动意味着需要新建 domain。

共享登录态可放在 `domains/session/`；登录表单和登录页面留在 `features/auth/`。禁止为了绕过模块边界把全部业务类型搬入 contracts。

### 4.4 通用能力

- `components/`：Button、Input、Modal 等无业务语义组件。使用主题令牌，文案由调用者传入或来自公共国际化资源。
- `hooks/`：无业务语义的通用 React hooks。不得依赖业务状态容器。
- `utils/`：无业务语义、无副作用的函数。网络、持久化和设备访问不放在这里。
- `theme/`：颜色、间距、字体等设计令牌。重复设计值应当使用令牌；零值、布局比例等结构性数值无需机械令牌化。
- 样式可以就近使用 `StyleSheet.create`；样式较多或影响阅读时拆成 `Xxx.styles.ts`。禁止在渲染逻辑中散落重复样式规则。

### 4.5 services：外部能力适配

- HTTP、存储、分析、推送及设备能力 SDK 必须经 services 封装，业务模块不直接创建 HTTP 客户端或调用存储 SDK。
- React、React Native、导航、TanStack Query、Zustand、表单、动画和 UI 库可以在职责适当的位置直接使用，不要求统一包装成 service。
- 上述框架直用权限不授予绕过适配器的权限：网络传输的 `fetch`、`XMLHttpRequest` 和自定义原生模块访问仍归对应 service。项目须列明所用外部能力 SDK 与受限调用入口；RN 的布局、组件和 app 生命周期 API 等按职责直接使用，不能仅按包名一律禁止 `react-native`。
- HTTP client 处理传输、超时、取消和通用错误归一化；业务错误文案、订单状态判断等由 feature 或 domain 处理。
- token 获取、失效通知等通过初始化参数或接口注入。services 不导入业务状态容器；会话刷新策略由 session 领域能力实现，由 app 连接到客户端。鉴权接口必须接收请求捕获的会话范围，并按 §4.8 校验归属，禁止旧请求在发送或重试时无条件获取当前账号的凭证。
- 更换服务实现时应当保持公开接口稳定，减少业务调用方变更；允许更新依赖清单、锁文件、原生配置和测试。无法保持同步/异步语义等契约时，须明确迁移影响。

**刷新与重试协调**

并发刷新、重放预算与失败释放的时间线和伪代码见[附录 A.4](./react-native-architecture-examples.md#a4)。

- 项目必须区分普通网络重试、凭证刷新后的鉴权重放和业务用例重试，并明确各自责任层、次数上限及一次逻辑操作的总请求次数或总时限。Query、HTTP client 与后台任务重试不得无协调地叠加；上层重新调用时不能无意重置该操作的预算。Query 重试机制见 [官方说明](https://tanstack.com/query/latest/docs/framework/react/guides/query-retries)。
- 普通网络重试默认由最接近调用目的的一层负责：已接入 Query 的请求由 Query 策略负责，HTTP client 默认不再叠加普通网络重试；非 Query 用例或任务可选择自身策略或显式启用 client 策略。确需多层重试时，必须传递并共同消耗有界预算，明确哪些错误允许重试；取消、会话失效及确定不可重试的业务错误不得作为普通网络故障反复尝试。
- 同一会话中需要刷新同一组凭证的并发请求必须合并进行中的刷新，由 session 管理等待者及刷新结果。迟到的旧凭证失败响应应先判断凭证是否已更新，不能为同一过期凭证重复启动刷新。独立运行时的刷新协调遵守 §5.4。
- 刷新请求仍经 services 传输，但必须采用明确的刷新专用路径或请求模式，禁止再次进入自身的自动刷新拦截链或等待自身刷新完成。刷新必须有超时与终止路径，成功或失败都须结束等待；临时网络失败与刷新凭证失效分别按 session 策略处理。登录、刷新与普通已认证请求的准入条件必须区分，避免会话恢复等待自身才能完成。
- 一次逻辑请求因鉴权失败触发的自动重放应当最多一次；项目确需不同上限时须明确依据，并纳入总预算。上层 Query 或用例重试不得将同一次失败重置成无限刷新机会。非幂等写操作即使只重放一次，也必须满足服务端幂等契约或可确认未执行等重放条件，不能仅凭鉴权状态码认定安全。
- 刷新、等待、重试与鉴权重放均继续遵守 §4.8 的会话归属和取消规则；基础设施只执行注入策略，不在 HTTP client 中决定业务补偿或界面提示。

### 4.6 状态与资源归属

- 页面临时状态优先使用组件本地状态；单 feature 状态放在该 feature；共享业务状态放在 domain。
- 客户端状态默认使用 React 本地状态；需要在子树共享时可以使用 Context，跨页面共享较复杂时可以使用 Zustand。业务状态的实现与更新入口由所属模块维护，app 仅负责必要的 Provider 组合。
- 不强制创建统一状态目录；少量状态可以就近放在组件或业务 hook 中，复杂后再在所属模块内拆分。
- 服务端缓存与客户端状态应当区分。若采用查询缓存方案，避免再把相同数据复制到另一份客户端状态，明确唯一事实来源和失效策略。
- 公共文案放在 `i18n/`；模块文案可就近放在 `locales/`，由 app 汇总注册并使用模块命名空间。i18n 引擎不得反向导入 features。
- 公共资源放在 `assets/`；模块私有资源就近放置。面向用户的静态文案必须接入国际化，日志和测试数据不受此限制。

### 4.7 TanStack Query 与 Zustand（推荐选型，按需采用）

本节不要求安装全部工具；一旦采用，对应的「必须 / 禁止」规则即适用。

| 状态类型         | 推荐方案                  | 示例                               |
| ---------------- | ------------------------- | ---------------------------------- |
| 页面临时状态     | `useState` / `useReducer` | 输入值、弹窗开关、当前选中项       |
| 子树共享状态     | props / Context           | 局部流程配置、组合组件交互         |
| 跨页面客户端状态 | Zustand，按需             | 多步操作草稿、跨页面筛选条件       |
| 服务端数据       | TanStack Query，推荐      | 用户资料、订单列表、详情、分页缓存 |

**目录与调用路径**

订单 API、query key、查询 hook、mutation 与非 React 收尾链路见[附录 A.2](./react-native-architecture-examples.md#a2)。

- QueryClient 创建和通用默认配置放在 `app/query/queryClient.ts`，QueryClientProvider 由 `app/providers/` 挂载。同一运行时作用域内客户端保持稳定，不得每次渲染重新创建；测试使用独立实例。后台任务如需查询缓存，由 app 显式提供所属作用域的客户端，不依赖 Provider 已挂载，见 §5.4。
- 查询 key、查询配置、查询与 mutation hooks 放在所属 `features/<name>/queries/` 或 `domains/<name>/queries/`。多个 feature 共同消费的数据应由所属 domain 提供公开入口，避免各模块重复定义同一业务查询。
- React 中的请求路径为「业务查询 hook → 模块 api 函数 → `@services/api` 公开能力」，适配器内部由 `client.ts` 等实现传输；非 React 用例或后台任务通过模块公开能力调用 api，按需使用注入的 QueryClient 能力。TanStack Query 管理所接入请求的生命周期与缓存，HTTP client 继续负责传输。
- 业务 React hooks 通过 `useQueryClient()` 获取客户端，不导入 `app/query/queryClient.ts`。非 React 的业务辅助函数通过参数接收所需客户端能力；services 不管理业务缓存。
- Zustand 状态按需放在所属模块的 `state/`，例如 `features/order/state/orderDraftStore.ts`。共享业务状态归 domain，不创建容纳所有业务的全局大 store。
- 跨模块访问仍遵守 §3；使用 QueryClient 或 Zustand 不授予跨 feature 读写权限。共享领域的缓存更新由其公开能力负责，用例所属 feature 决定协作流程，app 仅连接所需公开能力。

**React Native 生命周期适配**

网络适配、app 全局监听及页面聚焦示例见[附录 A.9](./react-native-architecture-examples.md#a9)。

- 项目必须明确断网恢复、应用回前台和页面重新聚焦时的查询策略；这些是不同触发条件，不得假定配置浏览器刷新选项即可自动接入 RN 事件。
- 启用网络恢复行为时，网络状态读取和订阅由 `services/network/` 等适配器提供，app 在 `app/query/lifecycle.ts` 中连接 `onlineManager`。必须处理初始状态、未知状态和订阅清理；读取失败时按项目策略处理，不把未知状态直接当作确认联网。
- 启用应用回前台刷新时，由 app 将 RN `AppState` 的初始状态与后续变化连接到 `focusManager`；监听必须在所属运行时中统一注册并可清理，不能由每个页面重复注册全局监听。基础设施适配器不直接管理 Query 缓存。
- 页面重新聚焦是否刷新、失焦后是否继续订阅或轮询，由所属 feature 结合导航生命周期与查询新鲜度决定；刷新范围限于相关查询，并避免初次挂载和首次聚焦造成非必要的重复请求。
- 具体 API 与清理方式须匹配项目锁定版本，机制见 [TanStack Query RN 指南](https://tanstack.com/query/latest/docs/framework/react/react-native)。

**数据所有权与缓存规则**

- 服务端数据由 Query 缓存维护，禁止为了共享再整份同步到 Zustand。编辑草稿可以独立保存，但必须明确初始化、提交成功、取消编辑及服务端更新时的处理方式。
- query key 必须使用可序列化数组，包含业务命名空间及决定查询结果的标识和参数，例如 `['order', accountId, 'detail', orderId]`。列表应纳入筛选条件；普通分页纳入页码，无限查询的游标通过其分页参数管理。key 由所属模块统一构造，禁止在其他模块手写其内部 key。
- 用户或租户相关查询必须包含对应身份范围；认证未就绪时不得发起依赖认证的查询。查询 key 的身份范围必须与请求捕获的会话范围一致；key 不包含 token 等凭证。key 用于缓存寻址，不能替代 §4.8 的会话有效性校验。Query 的 key 机制见 [官方说明](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)。
- 必须明确默认 `staleTime`、`gcTime`、重试和自动刷新策略，并允许查询按业务覆盖；重试覆盖仍须满足 §4.5 的责任层与总预算。`staleTime` 表示数据保持新鲜的时间，`gcTime` 控制未使用缓存的回收时间，不把两者混为一谈。
- mutation 改变已缓存的服务端数据时，必须明确相关缓存的更新或失效策略，不能默认刷新全部查询。没有关联缓存的操作（例如仅发送验证码或提交反馈）无需更新或失效缓存。采用乐观更新时必须处理失败回滚和后续数据校准；非幂等操作不得盲目自动重试。
- 请求的取消信号应当沿查询函数、模块 api 传递到 HTTP client。跨账号返回的旧请求或 mutation 回调不得写入新账号状态。

**mutation 副作用与并发更新**

页面回调与业务收尾的分工见[附录 A.2](./react-native-architecture-examples.md#a2)，并发覆盖反例及保守处理方案见[附录 A.5](./react-native-architecture-examples.md#a5)。

- 缓存更新或失效、必要回滚及业务收尾必须由所属模块的 mutation 配置或用例能力负责，不能只放在组件调用 `mutate(data, { onSuccess, onError, onSettled })` 时传入的回调中。这些单次调用回调可能在组件卸载后不执行，连续调用时也不保证逐次执行，机制见 [官方 mutation 指南](https://tanstack.com/query/latest/docs/framework/react/guides/mutations)。
- 单次调用回调可以处理当前页面的提示、关闭弹窗等界面行为；涉及导航或会话状态时仍须校验有效性。React 入口与非 React 用例、后台入口必须复用所属模块的必要收尾能力；不能让后台调用只执行 api 写入却遗漏共享缓存的一致性处理。同一操作的收尾由明确的一处调用，避免 useCase 和 hook 重复失效或回滚。
- 上述保证针对运行时仍存活的组件卸载或导航切换；需要在进程终止后继续完成的操作必须另行定义持久化及恢复策略，不能把内存回调视为可靠任务队列。
- 同一会话内可能并发修改同一实体或重叠缓存时，所属模块必须明确冲突范围与策略，例如按实体串行、基于服务端版本拒绝旧结果、按操作记录回滚，或暂不采用乐观更新。不要求所有 mutation 全局加锁；只串行发送网络请求并不自动保证此前的乐观修改可安全回滚。
- 采用乐观更新时，回滚只撤销本次操作仍拥有的变更，禁止无条件用旧快照覆盖后续有效更新；成功响应也不得无条件用旧版本覆盖新结果。最终查询校准必须与仍在进行的相关操作协调，避免重新获取的数据擦除尚未完成的乐观修改。服务端版本或冲突语义缺失时，应选择能验证正确性的保守策略。
- 至少考虑“操作 A 先发起，B 后发起且成功，A 最后失败或返回旧结果”的顺序；预期结果应保留 B 的有效更新，并遵守 §4.8 的会话隔离。

**Zustand 使用规则**

字段白名单、账号分区与恢复门禁示例见[附录 A.10](./react-native-architecture-examples.md#a10)。

- 组件应当按需选择订阅字段，状态修改通过所属模块的明确操作入口完成；禁止跨模块任意 `setState` 修改内部结构。
- 不把 Query 的加载状态、错误和查询结果另存一份到 Zustand。Zustand 只维护独立的客户端状态。
- 持久化按需开启，存储适配必须经过 `services/storage/`，明确保存字段、版本迁移和清理方式。异步恢复完成前，不得把初始默认值当作已恢复的最终状态；相关机制见 [Zustand 持久化文档](https://zustand.docs.pmnd.rs/reference/integrations/persisting-store-data)。

退出登录、账号切换及持久化恢复统一遵守 §4.8；这些会话规则不以采用 TanStack Query 或 Zustand 为前提。

### 4.8 会话归属与账号切换

最小会话范围、失效校验及同账号重新登录时间线见[附录 A.3](./react-native-architecture-examples.md#a3)。

本节适用于具有登录态或租户切换能力的项目，不强制引入状态库或查询库。

- session 模块维护账号、适用时的租户及会话代次。会话代次是区分登录会话的非凭证标识；退出登录、切换账号或租户、重新建立登录会话时必须使旧代次失效，同账号退出后重新登录也不复用旧代次。同一会话内正常刷新 token 不改变代次。运行时重建后的代次不得与可能恢复的旧操作混淆。
- 需要认证的 query、mutation、后台任务及其重试必须捕获发起时的会话范围。首次实际发送、等待队列恢复以及刷新后重试时，必须校验该范围仍有效，才能取得该会话的凭证；会话已变更则终止旧操作。允许使用同一会话刷新后的 token，禁止将旧操作自动改绑到新会话。
- 会话有效性和刷新决策由 session 的公开能力提供；HTTP client 通过注入接口执行校验，不读取业务 store。供 services 使用的最小范围类型与鉴权接口可以放在 `contracts/`，session 的业务实现仍留在 domain。异步获取凭证后、交给底层传输前必须再次校验，避免等待期间会话变化。
- 异步结果提交到业务状态、缓存、导航或持久化之前必须校验会话范围；失败回滚、刷新结果、失效通知与延迟回调同样受约束。不能只比较账号 ID，也不能让旧请求的鉴权失败清除新会话。取消信号只是减少无效工作，不能替代归属校验，也不能撤销已到达服务端的写操作。

账号切换由 app 调用 session 与所属模块公开能力协调，必须保证以下顺序约束：

1. 先使旧会话代次失效并关闭依赖认证的操作入口；新会话在恢复和隔离处理完成前保持未就绪。
2. 停用旧查询，取消可取消的请求，停止或隔离旧会话的重试队列、订阅及持久化写入；旧操作不能随网络恢复自动以新会话身份执行。
3. 调用所属模块的缓存清理、客户端状态重置和持久化清理或隔离能力。新会话访问共享状态前必须完成重置；可并行执行的清理也须满足这一完成条件。清理失败时不得继续暴露未隔离的旧状态，项目须明确重试或保持未就绪的处理方式。
4. 新会话恢复通过归属校验后再开放查询与业务操作。旧任务的结果即使稍后返回也不得提交。

持久化数据按账号及适用时的租户分区；恢复任务必须捕获目标范围和当前代次，应用恢复结果前重新校验。旧会话的在途写入必须完成、取消或与新会话物理隔离，避免清理后被旧写入重新填回。相同账号的新会话是否恢复既有草稿或缓存由项目明确，不能自动恢复旧会话尚未完成的写操作；恢复待执行操作须重新校验归属及重放条件。公共缓存是否保留由项目策略决定。

## 5. 跨模块协作与生命周期

### 5.1 协作方式

按协作目的选择方式，不把全局状态或事件总线作为默认中转站。

| 需求                        | 方式                                                                    |
| --------------------------- | ----------------------------------------------------------------------- |
| 共享业务状态或模型          | 所属 domain 的公开接口与业务 hooks                                      |
| 页面跳转                    | 公共路由契约与最小路由参数                                              |
| 父子组件交互                | props、回调、组合                                                       |
| 跨模块业务流程              | 一个用例所属 feature 持有流程，调用 domain 公开能力或自身声明的注入接口 |
| 连接两个 feature 的公开能力 | app 将提供方公开能力适配到消费方声明的接口，业务流程留在消费方用例内    |
| 通用外部能力                | services 的公开接口                                                     |
| 无法直接组合的异步通知      | 可选的类型化事件机制，说明必要性、订阅清理和错误处理                    |

事件机制不得用于绕过状态所有权和模块边界，不得成为关键业务流程不可追踪的隐式调用链。

**用例归属与依赖注入**

接口、实现注入与 fake 测试的代码示例见[附录 A.1](./react-native-architecture-examples.md#a1)。

- 一个完整业务流程必须有明确所有者，通常为表达该用户目标的 feature；流程较复杂时可以放在其 `useCases/`。不为目录对称而拆成多个 feature，也不强制新增全局流程层。
- 优先消费已有 domain 的公开能力。确需连接另一个 feature 时，消费方在自身模块声明最小输入、输出与所需操作接口，通过公开入口或 `registration.ts` 暴露装配所需的工厂、Provider 或类型；app 导入双方入口并注入实现。消费方不导入提供方的类型或实现，提供方也不反向导入消费方契约。
- 注入接口必须表达明确业务能力，不能传入整个模块、任意 service locator、全局 store 或事件总线。app 的适配仅转换接口形状并传递调用，不决定业务成功条件、执行顺序或补偿策略。

例如「创建订单 → 支付 → 处理支付结果」由 `features/checkout/useCases/submitCheckout.ts` 持有：

| 位置                     | 示例职责                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| checkout 用例            | 定义所需的创建订单、发起支付、查询支付结果等接口；决定先创建后支付；区分成功、明确失败和结果未知 |
| 提供方 domain 或 feature | 通过公开能力执行创建订单或支付，返回约定结果；维护各自业务规则及其缓存                           |
| app 装配                 | 选择提供方实现并注入 checkout；不在连接回调里编写支付失败后的业务处理                            |
| checkout 测试            | 注入 fake 验证成功路径、创建失败时不支付、支付结果未知时进入核验分支等行为                       |

该示例中，创建订单失败则停止后续支付；支付明确失败时，用例按产品规则保留待支付状态或发起补偿；支付超时等结果未知时先进入结果核验，不能直接视为未扣款并自动重新支付。是否取消订单、何时允许用户重试由用例规则决定。各操作仍须遵守 §4.8 的会话绑定，补偿和重放不能绕过服务端幂等及结果核验要求。

### 5.2 新增模块

- 按 §3.3 创建必要目录和最小公开入口；自定义入口同步项目入口约定与边界配置，有平台差异时按 §2.3 验证各实现。
- 有页面时新增路由契约并注册导航；无页面的模块不需要路由。
- 有 Provider、初始化入口、翻译资源时，通过装配入口注册；存在后台任务时补充 §5.4 的非 UI 初始化与清理约定。
- 检查依赖边界、用例所有者、状态归属、文案和主题使用；新增 domain 依赖时同步例外清单与检查配置。采用查询缓存时补充 key、失效、mutation 收尾与并发策略及 RN 生命周期策略；请求重试遵守 §4.5，涉及认证时遵守 §4.8。
- 为变更的业务行为补充适当测试，完成 §8 的检查。

### 5.3 删除模块

注册点与对应删除动作的对照示例见[附录 A.8](./react-native-architecture-examples.md#a8)。

删除模块目录，并清理显式注册点：导航和路由类型、Provider、初始化入口、后台任务、生命周期订阅、注入连接、翻译资源、深链接配置及相关测试；按需清理缓存、状态重置注册点和持久化数据。同步移除失效的 domain 依赖例外与检查配置。共享 domain 只有在不存在调用方时才移除，调用方包括经批准的其他 domain。

「可独立移除」指依赖边界清晰、清理位置可追踪，不承诺删除一个目录即完成全部卸载工作。

### 5.4 运行时与后台任务初始化

并发初始化复用、失败回收及前后台调用示例见[附录 A.6](./react-native-architecture-examples.md#a6)。

有后台任务或组件挂载前调用业务能力时，必须提供不依赖 React 挂载的初始化路径；不要求所有模块实现统一生命周期接口。

- 根 `index.js` 按平台要求及时注册任务处理函数，处理函数通过 `app/bootstrap/` 的装配入口等待必要初始化，再调用 feature 或 domain 的非 React 公开能力。不得等待 UI 挂载、调用 hooks 或依赖 Provider 已运行。后台任务机制见 [RN Headless JS 文档](https://reactnative.dev/docs/headless-js-android)。
- app 的初始化入口应当返回明确的就绪结果与所需依赖，例如 `ensureRuntimeReady()`；同一运行时内并发调用必须合并进行中的初始化，重复调用不能重复注册监听、拦截器或启动任务。模块导入本身不应当启动这些副作用。
- 必须明确初始化完成条件：所需配置、服务连接、适用时的会话恢复，以及所用持久化状态已完成恢复或确定可用的降级状态。失败必须对调用方可见；不得以部分初始化对象冒充就绪结果。重试前须处理已完成的局部初始化，避免重复副作用。
- 前台与后台共享同一 JS 运行时时复用已就绪依赖；独立运行时时各自初始化，不假设内存单例、QueryClient 或会话代次跨运行时共享。项目必须明确运行时作用域；有多运行时并发存储或鉴权时，须通过可跨运行时观察的会话有效性机制及存储协调保证 §4.8，不能仅检查各自内存中的旧登录态。
- 后台任务使用 QueryClient 时，由 app 通过参数提供所属运行时或明确任务作用域的实例；任务仅操作所属模块及会话的缓存。实例的共享、销毁和持久化策略必须明确，不能在每次任务回调中无意创建竞争的客户端。
- 任务入口只负责装配和调用；业务顺序、失败处理及重试策略归所属模块，任务重试与底层请求共享 §4.5 规定的预算。任务必须返回能反映完成或失败的 Promise，遵守平台期限，并检查任务携带的账号或租户与有效会话一致；缺少有效认证时按任务规则终止或延后，不能自动以当前另一个账号执行旧任务。
- 监听、拦截器和资源必须有明确清理责任：任务私有资源由任务结束路径清理，运行时共享资源由 app 生命周期管理；不能在单个任务结束时销毁前台仍使用的共享依赖。测试和运行时重建必须能够清理旧注册。

### 7.1 TypeScript 别名

以下为合并到现有配置的示例。保留项目使用的 RN TypeScript 基础配置及必要选项。

```json
{
  "extends": "@react-native/typescript-config",
  "compilerOptions": {
    "paths": {
      "@app/*": ["./src/app/*"],
      "@features/*": ["./src/features/*"],
      "@domains/*": ["./src/domains/*"],
      "@components/*": ["./src/components/*"],
      "@hooks/*": ["./src/hooks/*"],
      "@utils/*": ["./src/utils/*"],
      "@theme/*": ["./src/theme/*"],
      "@services/*": ["./src/services/*"],
      "@contracts/*": ["./src/contracts/*"],
      "@config/*": ["./src/config/*"],
      "@i18n": ["./src/i18n/index.ts"],
      "@assets/*": ["./src/assets/*"]
```

本方案使用 `@components/Button` 等组件级入口，不使用裸 `@components`。需要新增目录总入口时，必须同时添加对应的精确 TS 映射。

别名只解决寻址，不授予导入权限。例如 `@features/order/hooks/useOrder` 即使可以解析，也仍违反公开入口规则。

### 7.2 Babel 别名

采用 `babel-plugin-module-resolver` 时，映射必须与 TypeScript 保持一致；以下内容应合并到现有 Babel 配置，不得删除其他库要求的插件或改变其必要顺序。

```js
module.exports = {
  presets: ["module:@react-native/babel-preset"],

      },

  ],

```

TypeScript 的 `paths` 不会改写输出导入路径。别名变更后必须验证 TypeScript、Metro 和 Jest 的实际解析。Jest 若未使用相同 Babel 转换链，须配置等价的 `moduleNameMapper`，避免同时维护互相冲突的映射。

### 7.4 架构规则自动化

例外记录、局部检查配置、命令与验收文件见[附录 A.7](./react-native-architecture-examples.md#a7)；平台解析配置见[附录 A.11](./react-native-architecture-examples.md#a11)。

项目必须使用 ESLint 边界规则或独立依赖检查器落实以下规则，并纳入 CI。仅配置普通语法 lint 不代表已完成架构检查。

- 必须完整落实 §3.1 的所有来源与目标区域，未列出的依赖默认拒绝，运行时和类型导入均受约束；不能只检查 feature、domain 和 app。新增生产目录必须归类后才能导入，检查器不能把未识别源码当作自动放行的区域。
- 生产代码禁止 feature 互引及下层反向引用 app；domain 之间只允许 §3.1 清单中明确批准的方向、入口、导出项和导入范围，并拒绝包括类型依赖在内的领域依赖环。
- 模块归类及公开入口按 §3.3 配置，禁止跨模块访问内部实现；生产代码中 `registration.ts` 仅供 app 导入，测试权限按 §3.4 配置。新增公开入口或改变模块粒度必须同步检查配置，别名解析成功不等于入口公开。
- 解析别名、相对路径、转导出、静态可确定目标的动态导入和 `require` 后再判断边界。依赖目标无法静态确定时，不得静默忽略，应改用显式映射或记录受控例外及其验证方式。
- 覆盖 `.ios`、`.android`、`.native` 及通用回退实现，按 §2.3 对每个支持平台构建实际解析图并检测运行时循环；类型依赖也须检查领域边界与领域依赖环。不得用单一默认解析结果代表全部平台，也不能把互斥平台的边混成运行时循环。
- 类型导入也必须符合依赖矩阵；不得以类型复用为由引用矩阵未允许的模块。domain 类型依赖例外不能自动扩大为运行时权限。
- 测试源码按 §3.4 区分本模块测试、app 装配测试、跨模块测试及辅助代码；禁止生产源码导入任何测试专用入口或文件。

外部能力边界必须维护与 §4.5 一致的 SDK、受限导出及调用入口清单，并落实以下覆盖约定：

| 检查对象                                                                | 自动化与评审责任                                                                                            |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| HTTP、存储、分析、推送及设备 SDK 的直接导入或 `require`                 | 自动限制在对应 services 适配器；测试权限按 §3.4。框架与 UI 库按职责允许，不将全部第三方包一律禁止           |
| 网络传输的全局 `fetch`、`XMLHttpRequest` 及项目已知的自定义原生模块入口 | 对可静态识别的调用配置语法或符号限制，识别导入别名及全局访问形式；不能仅依赖包名限制                        |
| SDK 再包装、注入后的能力用途或工具不能识别的间接调用                    | 在评审中检查实际职责和调用路径，并记录自动化未覆盖的范围；可静态识别的直接违规不能一律推给评审              |
| SDK 必须在根入口进行的早期注册等例外                                    | 按具体文件、包与必要调用记录项目级适配，优先由 app 调用 service 公开注册能力；禁止放开整个 app 或全部根文件 |

新增或修改边界配置时必须用少量允许/拒绝样例验证结果，至少覆盖本次修改涉及的情形。以下是配置验收样例，不要求在业务工程创建这些示例模块：

| 情形                                                                      | 预期                                 |
| ------------------------------------------------------------------------- | ------------------------------------ |
| feature 通过公开入口访问 domain                                           | 允许                                 |
| services 通过公开入口访问 utils，components 通过公开入口访问 hooks        | 允许                                 |
| services 导入 components、utils 导入 services、theme 导入业务模块         | 拒绝，类型或运行时导入均不能绕过矩阵 |
| 合法调用方引用 `@hooks/useDebounce`、`@utils/date`、`@services/api`       | 允许，分别按单文件或目录入口识别     |
| 外部引用目录树中的 `@utils/date/formatDate` 或 `@services/api/client`     | 拒绝                                 |
| 任一平台实现越界，或该平台实际依赖图中存在运行时循环                      | 拒绝；不能因其他平台通过而放行       |
| 两个互斥平台的依赖边合并后似乎成环，但各平台实际图均无环且边界合法        | 不按运行时循环误报                   |
| 业务模块直接导入受限存储 SDK 或调用网络传输 `fetch`                       | 拒绝；对应 service 内合法传输允许    |
| checkout 不导入另一个 feature，由 app 导入双方公开入口并注入能力          | 允许；流程归属另由用例测试及评审检查 |
| cart 按仅类型白名单从 product 的公开入口导入指定类型                      | 允许                                 |
| 上例改为运行时导入、内部深路径、未列出的导出项或新增反向依赖              | 拒绝                                 |
| 通过相对路径、转导出或动态导入访问另一个 feature                          | 拒绝                                 |
| 模块内测试访问本模块内部实现及私有测试辅助代码                            | 允许                                 |
| 根集成测试访问公开入口和指定 app 测试装配入口                             | 允许                                 |
| 根集成测试访问 feature 内部文件，或模块测试访问另一个模块私有测试辅助代码 | 拒绝                                 |
| 生产模块导入测试辅助代码或测试装配入口                                    | 拒绝                                 |

没有自动化覆盖的语义规则或特殊语法仍须在评审中检查，不能宣称已经全部自动强制；不能用评审替代本节明确要求的基础边界检查。

## 8. 测试与验证

| 类别                        | 要求                                                                                                                                                                                     |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 单元和组件测试              | 就近放置；覆盖业务规则、状态转换和关键交互，避免仅复述实现                                                                                                                               |
| 跨模块集成测试              | 放在根 `__tests__/`，通过公开入口及指定 app 装配入口验证共享状态和模块协作，遵守 §3.4                                                                                                    |
| 网络隔离                    | 自动化单元/集成测试不依赖真实外部服务；在适当边界使用 mock 或本地受控服务                                                                                                                |
| API 测试                    | 测业务映射时可替换 HTTP client；测试 client 本身时保留 client，替换底层传输，验证超时、取消、鉴权注入、发送前归属校验和错误处理                                                          |
| 刷新与重试（采用时）        | 验证并发过期请求合并刷新、迟到旧凭证响应不重复刷新、刷新失败或超时结束等待、刷新不递归；验证上层重试与鉴权重放不突破总预算，取消和不可重试错误及时停止                                   |
| 用例编排                    | 用注入替身验证执行顺序、成功与失败分支、结果未知时的核验及补偿条件；确保 app 装配不承载这些决策                                                                                          |
| 会话隔离（有认证时）        | 验证 A→B、A→退出→A、租户切换、切换期间刷新完成，以及旧请求排队或重试；断言旧操作不携带新会话凭证发送，旧成功、失败和回滚不影响新会话                                                     |
| 状态与缓存（采用时）        | 验证关联 mutation 的缓存更新，以及无关联缓存时不触发无意义失效；验证账号切换和持久化恢复竞争，包括旧恢复晚到、旧写入在清理后完成；各测试重建或重置 QueryClient 与 Zustand 状态，避免串扰 |
| mutation 生命周期（采用时） | 提交后立即卸载页面或切换导航，必要缓存更新及业务收尾仍执行；验证连续调用逐次完成必要处理，非 React 入口复用收尾且不会重复执行                                                            |
| 并发更新（存在时）          | 同实体 A 先发、B 后发且成功，A 随后失败或返回旧结果；验证不覆盖 B，并验证相关查询校准不会擦除仍在进行的有效乐观修改                                                                      |
| RN 查询生命周期（采用时）   | 模拟网络恢复、前后台切换和页面聚焦，验证预期刷新范围、未就绪时的请求门禁及监听清理；确认初次聚焦不造成非必要重复请求                                                                     |
| 后台初始化（采用时）        | 在未挂载 React 树时执行任务；验证并发初始化只执行一次、部分失败与重试、账号不匹配时不执行，以及任务资源清理不破坏共享运行时；存在多运行时时验证跨运行时会话失效与存储协调                |
| 服务替换                    | 验证公开契约，例如缺失值、序列化、异步语义及异常行为                                                                                                                                     |
| 平台实现（存在时）          | 各支持平台对同一入口执行类型与契约验证，覆盖可用性及不支持结果；Jest 按平台配置分别解析，或使用等价的平台测试机制，不只测试通用回退文件                                                  |
| 端到端测试                  | 按项目风险覆盖登录、关键业务流程；使用隔离测试环境                                                                                                                                       |

CI 必须执行 lint（含架构检查，或独立执行等价检查）、typecheck 和 test。存在平台实现时，类型检查与边界检查须使用覆盖各支持平台的解析配置；测试按变更范围验证受影响实现。别名、Metro、Babel、入口、平台实现文件或依赖配置变更必须增加受影响平台的打包解析验证；原生配置或依赖变更必须验证受影响平台的构建。发布前完成项目支持平台的发布构建与关键流程检查。

## 9. 代码评审清单

以下项目按变更范围检查，不适用项标记 N/A，不为满足清单创建空实现。

- [ ] 新代码归属明确，业务实现位于 feature 或 domain。
- [ ] 所有源码区域均已归类并完整受依赖矩阵检查，未通过相对路径、别名、转导出或 require 绕过边界。
- [ ] domain 依赖例外的方向、入口和导入范围与评审记录及检查配置一致，无领域依赖环。
- [ ] 模块粒度与公开入口符合 §3.3，变更已同步入口约定和检查配置，装配出口未被业务模块导入。
- [ ] 跨模块用例有明确所有者，执行顺序与失败处理保留在业务模块，app 仅注入和连接能力。
- [ ] 业务状态由所属模块维护，app 仅组合必要的 Provider，services 未直接读取业务状态。
- [ ] 采用 Query/Zustand 时数据未重复维护，key 与身份范围一致，仅按关联数据执行缓存更新或失效。
- [ ] mutation 的必要收尾不依赖页面单次回调，非 React 入口复用处理，同实体并发更新和回滚不会覆盖后续有效结果。
- [ ] 有认证时，发送、刷新、重试、回调及持久化均校验会话归属，同账号重新登录不会接收旧会话结果。
- [ ] 同会话刷新合并且不递归，重试责任层和鉴权重放上限明确，各层共同遵守总预算。
- [ ] RN 查询的网络、应用焦点和页面焦点策略明确，订阅有统一注册与清理责任。
- [ ] 后台任务可在 React 未挂载时完成初始化，失败可见，运行时共享和资源清理责任明确。
- [ ] 共享业务组件未混入通用 UI，未为复用制造不必要抽象。
- [ ] 新路由和注册点完整，参数遵守共享契约。
- [ ] 外部能力通过 services 使用，SDK 和受限调用清单已同步自动化规则，未覆盖的间接调用及例外有明确评审记录。
- [ ] 用户文案、主题和资源归属合理。
- [ ] 配置与锁定版本一致，新增别名已验证实际解析。
- [ ] 平台实现保持统一公开契约，各支持平台的边界与循环检查、类型验证及受影响平台的测试和打包解析已完成。
- [ ] 测试按权限访问公开或内部入口，生产代码未引用测试辅助代码，边界配置变更已验证允许与拒绝样例。
- [ ] 与变更风险相匹配的测试和构建检查已通过。
