# APP 工程开发规范

> 版本：v1.1.0
> 生效日期：2026-09-01
> 适用范围：iOS、Android、React Native、Flutter 及其他 Hybrid APP
> 文档性质：团队工程强制规范
> 上位约束：本仓库项目宪法、Git 宪章及适用的后端工程宪章

## 1. 目标与适用原则

本规范用于统一 APP 的需求、设计、开发、测试、发布、运营和 AI 辅助开发行为，确保产品具备可维护、可测试、可观测、可恢复和可持续演进的工程基础。

文中关键词含义如下：

- **必须**：强制要求；不满足则不得合并或发布。
- **应**：默认要求；如不采用，必须在变更说明中记录理由。
- **可以**：允许选择，不构成强制约束。

当多份规范冲突时，依次遵循：项目宪法、法律与合规要求、本规范、已批准的 Feature Spec、团队约定。低优先级文档不得降低高优先级规则。

所有工程决策按以下顺序处理：

```text
安全性 > 数据正确性 > 业务正确性 > 稳定性 > 可维护性 > 性能 > 开发效率
```

任何“快速上线”理由都不能绕过安全、数据正确性和质量门禁。

## 2. 设计决策原则

### 2.1 简单、清晰、可验证

默认选择最简单且能够满足当前规格的方案。新增抽象、框架、状态层或第三方依赖前，必须说明其解决的当前问题、替代方案和长期成本。

强制遵循 KISS、YAGNI 和有限度的 DRY：少量重复优于错误抽象，业务知识重复必须治理，纯代码形状相似不构成抽象理由。

### 2.2 证据优先

API 字段、业务规则、权限行为、支付状态、SDK 能力和兼容性不得凭空猜测。实现前必须查阅规格、接口契约或平台官方文档；仍无法确定时，必须在规格中标注假设并获得确认。

### 2.3 变更最小化

一次变更只解决一个明确目标。功能开发、无关重构、全量格式化和依赖升级应拆分为独立变更；确需合并时，必须说明原因和影响范围。

## 3. 工程分层与依赖规则

APP 默认采用以下依赖方向。箭头表示“编译期依赖”：

```text
Presentation ──→ Application ──→ Domain
                       │             │
                       └──────→ Port ←──── Infrastructure

App/Composition Root 负责装配各层实现，不承载业务规则
```

### 3.1 Presentation

负责页面、组件、导航适配、用户事件转发和 UI 状态渲染。不得直接访问 HTTP、数据库、第三方 SDK 或承担核心业务规则。

### 3.2 Application

负责用例编排、事务/流程边界、加载与取消策略、跨端流程协调，以及把领域结果转换为展示所需状态。Application 不应成为所有业务规则的集中地。

### 3.3 Domain

负责实体、值对象、业务状态、纯业务规则和领域错误。应尽量平台无关，不得依赖 UI 框架、网络库、数据库、原生 SDK 或第三方支付/统计 SDK。

### 3.4 Port

负责定义领域或应用层需要的抽象能力，例如用户仓储、支付网关、设备能力、时间提供者和分析接口。接口应小而专，不暴露基础设施细节。

Port 的所有权属于调用方：领域规则所需接口放在 Domain，流程编排所需接口放在 Application。禁止为了“统一”建立包含大量无关方法的通用 Repository 或 Service 接口。

### 3.5 Infrastructure

负责 API 客户端、DTO、Mapper、数据库、缓存、Secure Storage、原生能力适配和第三方 SDK 封装。所有外部失败必须映射成上层可处理的错误，不得静默吞掉。

禁止以下调用：

```text
Page/Screen → HTTP / Database / SDK
Domain      → UI / Platform SDK / HTTP Library
Feature A   → Feature B 的内部实现或私有状态
```

## 4. 模块与目录规范

按业务能力组织模块，避免全局堆积 `components`、`services`、`utils`、`models`、`pages` 等技术型目录。推荐结构如下：

```text
src/
├── app/                         # 启动、根导航、环境装配
├── core/                        # 与具体业务无关的基础能力
│   ├── network/
│   ├── storage/
│   ├── logging/
│   ├── analytics/
│   ├── security/
│   └── platform/
└── features/
    └── <feature>/
        ├── presentation/
        ├── application/
        ├── domain/
        └── infrastructure/
```

Feature 必须拥有明确公开接口；跨 Feature 访问只能通过公开用例、查询接口、事件或导航协议完成。不得访问其他 Feature 的内部文件、内部状态或数据库表。

`core` 只能承载无业务语义且至少被两个模块稳定复用的能力。仅被单个 Feature 使用的代码必须留在该 Feature 内；禁止把 `core`、`common`、`shared` 演变为无边界的公共垃圾场。

每个 Feature 应公开一份最小契约，至少说明入口、输入、输出、错误、线程/生命周期约束和所有权。跨 Feature 事件必须有稳定名称、版本和载荷定义；事件不得替代本应同步返回的明确结果。

## 5. 规格驱动开发流程

除文字澄清、纯格式调整和无行为变更的机械修改外，所有变更必须先形成可评审规格。流程为：

```text
需求 → 规格 → 设计 → 任务拆分 → 实现 → 测试 → 评审 → 验收 → 发布 → 监控
```

Feature Spec 至少包含：

- 背景、目标、非目标和影响范围
- 用户流程、页面入口、导航和权限要求
- 业务规则、状态模型和数据流
- API/本地数据契约及兼容策略
- Loading、Empty、Error、Offline、Retry 和恢复行为
- 安全、隐私、性能和埋点要求
- 风险、回滚方案和明确的验收标准

复杂功能必须能描述：

```text
User Action → UI → UseCase → Repository/Port → API/DB
            → Domain → UI State → UI
```

本仓库变更应使用 OpenSpec 等规格载体；需求变化时先更新规格，再改实现。

规格必须将验收标准写成可验证结果，优先使用 Given/When/Then 或等价表达。禁止使用“体验良好”“性能较快”“兼容主流设备”等无法客观判定的描述。

风险满足以下任一条件时，技术设计必须单独评审：涉及支付、账号、隐私、加密、数据迁移、远程控制、跨 Feature 公共契约、启动链路或不可逆操作。

## 6. UI 与组件规范

### 6.1 状态驱动

页面必须根据显式状态渲染，不得依赖多个隐含布尔值拼接页面生命周期。至少考虑：

```text
Idle / Loading / Refreshing / Success / Empty / Error / Offline
```

复杂功能应显式建模业务状态、网络状态、操作状态和恢复状态。关键状态不得只用 `isPaid`、`isConnected` 等单一 Boolean 表达完整生命周期。

### 6.2 页面与组件

页面负责展示、事件接收、导航和状态绑定；ViewModel/Controller 负责交互状态；UseCase 负责业务流程。组件必须有明确输入输出、单一职责和可独立测试的边界。

组件出现以下任一情况时，应拆分或重新划分职责：超过约 300 行、包含多个业务区域、嵌套条件明显膨胀、同时处理数据和展示、难以单测。行数只是信号，职责边界优先。

组件不得隐藏发起请求、修改全局状态或依赖特定页面上下文的副作用。

### 6.3 交互完整性

每个异步操作必须定义：触发条件、进行中反馈、重复点击策略、成功反馈、失败反馈、取消方式和恢复路径。列表必须考虑分页、空列表、加载更多失败、下拉刷新和重复请求。

### 6.4 设计系统与无障碍

颜色、字体、间距、圆角、阴影、图标和动效必须优先使用统一 Design Token 或设计系统组件，不得在业务页面散落魔法值。业务组件不得复制基础组件已经提供的交互状态。

所有可交互元素必须具备可访问名称、正确语义和足够点击区域；文本必须支持系统字号缩放。颜色不能作为传递状态的唯一方式。关键流程必须通过屏幕阅读器、键盘/外接输入设备（平台适用时）和高对比度检查。

## 7. 状态、数据与模型

必须区分：

```text
Local State | Feature State | Global State | Server State | Persistent State
```

默认使用最小作用域：Local 优先于 Feature，Feature 优先于 Global。全局状态仅用于真正全局且生命周期明确的信息，例如登录会话、主题、语言和当前设备上下文。

网络数据必须经过模型边界：

```text
API JSON → DTO → Mapper → Domain Model → UI Model
```

DTO 不得直接作为 UI 数据模型。后端字段变化应尽量被 Mapper 隔离；缺失、未知和新增字段必须有兼容策略。

缓存必须定义数据来源、缓存键、有效期、失效条件、刷新策略和一致性要求。缓存不得成为关键业务事实的唯一来源；用户退出登录、切换租户或切换账号时，必须清理或隔离对应数据。

并发写入必须明确“最后写入优先”、版本号、串行化或冲突合并策略。不得依赖请求自然返回顺序保证最终状态。

## 8. 网络与错误处理

所有 HTTP 请求必须经过统一 Network Layer，集中处理 Base URL、超时、认证头、Trace ID、重试、取消、日志、错误映射和 Token 刷新。业务代码不得直接调用 `fetch`、`axios`、`Retrofit` 或 `URLSession` 等具体客户端。

自动重试默认只适用于幂等请求和明确可恢复错误，并采用有上限的指数退避与抖动。认证刷新必须防止并发刷新风暴；刷新失败后应原子地结束会话并避免无限重试。

错误至少归类为：

```text
Network / Authentication / Authorization / Validation
Business / Storage / Device / Timeout / Cancelled / Unknown
```

底层异常不得直接展示给用户；用户提示必须可理解，日志必须保留诊断信息。任何重要失败至少满足以下一项：用户可感知、日志可追踪、监控可发现或系统可恢复。

系统默认假设网络会断、请求会超时、响应会延迟、请求会重复、缓存会失效、APP 会被杀死。关键请求必须明确 Timeout、Retry、Idempotency、Cancellation、Offline 和恢复策略。

API 契约必须明确成功码、业务错误码、可空字段、分页语义、时间与金额格式。客户端不得把所有非 2xx 响应统一映射成“网络错误”。

## 9. 安全与隐私

遵循“永不信任客户端、网络和外部输入”。客户端不能作为支付成功、会员权益、价格、资源所有权或设备权限的最终裁决者；最终状态必须由可信服务端确认。

存储要求：

```text
Token/密钥/敏感凭据 → Keychain / Keystore / Secure Storage
结构化业务数据     → 数据库
普通缓存             → Cache
临时 UI 数据         → Memory
```

禁止明文保存密码、Token、支付凭据或身份敏感信息；禁止将敏感信息写入普通日志、崩溃报告、埋点参数或 URL。Deep Link、推送和外部输入必须进行格式、权限、登录态和资源归属校验。

敏感数据必须执行最小收集、最小存储、最短保留和最小访问原则。引入采集用户数据的 SDK 前，必须完成数据项、用途、共享对象、保存期限、删除机制和用户同意方式审查。

禁止依赖代码混淆、证书锁定或客户端加密隐藏服务端密钥。客户端内置内容一律视为可被提取；真正的服务端凭据不得下发到 APP。

权限采用“使用时请求”，请求前说明用途，并完整处理 Granted、Denied、Restricted、Unavailable、Never Ask Again 等状态。权限拒绝不得导致崩溃或无限弹窗。

## 10. 关键业务规范

### 10.1 幂等与状态机

创建订单、支付确认、恢复购买、领取权益、设备指令、上传任务等操作必须具备幂等键或等价机制。重试不得造成重复扣款、重复订单、重复权益或重复指令。

支付状态必须显式建模，例如 `CREATED`、`PENDING`、`PROCESSING`、`SUCCESS`、`FAILED`、`CANCELLED`、`REFUNDED`。客户端支付回调、服务端通知和主动查询必须最终收敛到同一订单状态。

金额使用最小货币单位整数或 Decimal，禁止用 Float/Double 做业务计算。日期时间内部使用 UTC 与 ISO 8601，展示时转换用户时区。

### 10.2 生命周期恢复

支付、上传、下载、设备升级、授权和登录等流程必须考虑前台、后台、挂起、恢复、强杀和重启。关键进度应持久化或可通过服务端查询恢复，不得假设 APP 始终存活。

恢复逻辑必须可重复执行，且不能重复产生业务副作用。恢复后应先与可信状态源对账，再决定继续、完成、失败或提示用户干预。

## 11. 导航、国际化与平台差异

导航必须集中定义 Route、Params、Result、Deep Link、Authentication Guard 和 Permission Guard。Feature 不得散落硬编码页面地址或形成不可追踪的跳转链。

用户可见文本不得硬编码，必须使用统一国际化资源键。日期、数字、货币、时区、文案长度、无障碍和 RTL（如适用）都应纳入验收。

Route 参数必须是可序列化、可校验且最小化的数据；不得通过导航参数传递大对象、敏感凭据或可过期的完整业务实体。Deep Link 必须具备版本兼容和未知路由兜底。

平台差异必须集中在 Platform/Device/Permission/Payment Adapter 等适配层，业务层禁止到处散落平台判断。

## 12. 配置、依赖与 SDK

环境至少区分 Development、Test、Staging、Production。URL、密钥、测试账号和 Feature Flag 不得散落硬编码；密钥不得进入仓库。

新增依赖必须评估必要性、维护状态、安全漏洞、License、包体积、平台兼容性、升级成本和替代方案。第三方 SDK 必须由 AnalyticsService、PaymentService、PushService 等稳定接口包装，业务代码不得直接依赖 SDK。

依赖版本必须锁定并可重复构建；自动升级不得绕过测试和评审。停止维护、存在已知高危漏洞或 License 不兼容的依赖不得进入发布版本。依赖移除时必须同时清理初始化、权限、配置、隐私声明和构建脚本。

Feature Flag 用于灰度、分群、紧急关闭和分地区启用；功能稳定后必须清理，不得形成永久分支逻辑。

## 13. 日志、埋点与可观测性

统一日志至少包含时间、级别、模块、traceId、脱敏用户标识、事件和消息。生产环境默认关闭无必要 DEBUG 日志。

禁止记录密码、Access/Refresh Token、支付凭据、身份证、银行卡、完整手机号和完整邮箱。用户标识、设备标识和请求参数按最小化原则脱敏。

关键流程应具备 Logs、Metrics、Analytics、Crash Reporting 和 Trace，至少覆盖启动失败、登录失败、网络失败、支付失败、设备连接失败、页面异常、JS Crash 和 Native Crash。埋点必须定义事件名、触发时机、参数字典、隐私等级和去重策略。

日志、监控和埋点是不同目的的数据：日志用于诊断，监控用于告警，埋点用于产品分析。不得用埋点代替错误日志，也不得通过日志绕过埋点的数据治理流程。

每个关键流程必须定义成功率、耗时和失败原因分布；告警必须包含阈值、负责人和处置入口。发布后应按版本、平台、系统版本和渠道观察指标，防止总体数据掩盖局部回归。

## 14. 性能与资源

性能必须基于测量。每个版本至少关注启动时间、首屏时间、页面加载时间、帧率、内存、CPU、网络流量、包体积和耗电量，并为关键指标设定目标或回归阈值。

禁止在主线程执行大型计算或同步 IO；长列表必须虚拟化；图片必须按显示尺寸加载并具备压缩、缓存、占位和失败状态；后台任务必须有取消、超时、重试和资源上限。

性能目标必须记录测量设备、系统版本、构建类型、网络条件、样本量和统计口径。优化前后必须使用相同口径对比，禁止用 Debug 构建结果代表生产性能。

## 15. 代码、测试与评审

代码必须通过项目统一 Formatter、Lint、静态分析、Type Check（适用时）和 Build。命名必须体现业务语义，函数输入输出和副作用必须明确；禁止 `handle`、`process`、`data1` 等无语义命名泛滥。注释解释 Why，不重复 What；TODO 必须包含原因、后续动作、负责人或关联任务号，并设置清理条件。

测试按风险组合：Domain/UseCase 单测、Repository/Network 集成测试、组件测试和关键流程 E2E 测试。核心业务至少覆盖正常、边界、错误、重复操作、网络失败、权限拒绝和状态恢复。Bug 修复必须先构造复现，再补回归测试。

Code Review 必须检查业务正确性、架构边界、异常与恢复、安全、性能、可测试性、兼容性、日志和数据隐私，不能只检查格式。

### 15.1 测试分层

测试必须稳定、可重复、可隔离，并可在 CI 中无人值守运行。单元测试不得依赖真实网络、真实系统时间、执行顺序或共享可变状态；外部依赖应通过 Fake、Stub 或可控测试环境隔离。

| 变更类型 | 最低测试要求 |
| --- | --- |
| 纯领域规则 | Domain 单元测试，覆盖正常、边界和非法输入 |
| 用例编排 | UseCase 测试，覆盖成功、依赖失败、取消和重复触发 |
| API/数据库/SDK 适配 | 契约或集成测试，覆盖映射与错误转换 |
| UI 状态或交互 | ViewModel/Controller 测试；关键组件补 UI 测试 |
| 支付、登录、迁移等关键流程 | 上述测试 + 关键路径 E2E/验收测试 |
| Bug 修复 | 修复前可失败、修复后可通过的回归测试 |

覆盖率用于发现测试缺口，不能替代断言质量。新增或修改的核心业务分支必须全部有测试；确实不可自动化的场景必须在变更说明中给出人工验证步骤和证据。

### 15.2 持续集成质量门禁

以下任一项失败，变更不得合并：

```text
Formatter / Lint / 静态分析失败
Type Check 或编译失败
单元测试或必需的集成测试失败
架构依赖规则检查失败
高危安全漏洞或敏感信息扫描失败
关键兼容性、迁移或验收检查失败
必需审批未完成
```

禁止通过跳过测试、降低告警级别、扩大忽略规则或删除断言使 CI 变绿。确有误报时，必须采用最小范围抑制并记录原因、负责人和清理条件。

## 16. 兼容、迁移与发布

实现必须考虑旧 APP/新 APP、旧 API/新 API、旧数据/新数据并存。API、数据库、存储、Route 或公共接口的破坏性变更必须标记 `BREAKING CHANGE`，提供迁移、兼容窗口和回滚方案。

本地 Schema 修改必须提供可验证 Migration，覆盖旧版本升级、重复执行、失败恢复和必要的回滚/降级策略。

正式版本发布前必须完成：

```text
规格验收 → Code Review → Formatter/Lint/静态分析/Type Check
→ Unit/Integration Test → Build → Smoke Test → 回归测试
→ 发布检查 → 灰度 → 监控确认
```

发布必须具备版本号、构建产物、变更说明、已知问题、回滚方式、负责人和监控指标。线上异常应优先止损、定位根因、修复并补充测试。

移动端无法保证已安装版本立即回滚，因此“回滚”必须至少包含：停止灰度、服务端兼容、Feature Flag 关闭、紧急修复版本和用户数据恢复预案。数据库迁移和服务端接口不得依赖新版本 APP 已全部安装。

发布产物必须来自受控 CI，确保签名、环境、版本号和源码提交可追溯。不得用开发者本机临时构建物替代正式发布产物。

## 17. Git 与 AI 协作

提交必须遵循 Conventional Commits，使用清晰、具体的中文 subject；一个提交只表达一个清晰意图。功能、测试、文档、格式化和依赖升级能够拆分时必须拆分。共享分支默认不得改写历史。

AI 是实现工具，不是架构和业务决策主体。AI 开始工作前必须确认规格、验收标准、模块边界、可复用能力、数据流和异常场景；生成代码前优先复用已有公开接口，但不得通过阅读无关实现扩大任务范围。

AI 不得编造 API、业务规则或 SDK 行为，不得以 TODO、空方法、伪代码或假 API 替代真实实现。完成后必须执行适用的 Formatter、Lint、静态分析、Type Check、Build 和测试；无法执行时必须在交付说明中明确未验证项目。

AI 修改既有实现时必须先确认工作区状态并保护用户未提交变更。不得擅自删除、覆盖、回滚或格式化任务范围之外的文件；不得为了通过检查而降低门禁。

## 18. Definition of Done

功能只有同时满足以下条件才算完成：

```text
[ ] 规格、非目标和验收标准已确认
[ ] 架构分层、Feature 边界和数据流清晰
[ ] 正常、空、加载、错误、离线和恢复状态完成
[ ] 权限、重复点击、弱网和生命周期场景完成
[ ] 安全、日志、埋点和隐私检查完成
[ ] 必要的单元、集成、组件或 E2E 测试完成并稳定通过
[ ] Formatter、Lint、静态分析、Type Check、Build 通过
[ ] 兼容性、迁移和回滚方案已确认
[ ] Code Review 与验收完成
[ ] 发布后监控指标和负责人已明确
```

## 19. 例外与修订

例外只能是有时限、有责任人、有风险控制的书面决定，必须记录：违反条款、业务原因、影响范围、风险等级、补偿措施、审批人、到期日期和清理任务。例外到期前未完成治理时，必须停止相关变更合并；不得自动续期。

安全红线、数据正确性、支付与权益最终确认、敏感信息保护不得豁免。工具故障造成的临时门禁例外必须保留等价人工证据，并在工具恢复后补跑检查。

规范修订必须说明明确问题、修改理由、影响范围和迁移计划，并遵循语义化版本：PATCH 仅文字澄清，MINOR 新增兼容规则，MAJOR 删除或改变核心规则。

## 20. 角色与责任

| 角色 | 最低责任 |
| --- | --- |
| 产品/需求负责人 | 明确目标、非目标、业务规则和验收标准 |
| 技术负责人 | 审核架构边界、风险、兼容与回滚方案 |
| 开发者 | 实现、测试、自检并提供验证证据 |
| Reviewer | 独立检查正确性、风险和规范符合性 |
| QA | 基于规格验证关键路径、异常和兼容场景 |
| 发布负责人 | 确认产物、灰度、监控、止损和回滚准备 |

同一人可以承担多个角色，但关键业务的实现者不得成为唯一审批者。

## Appendix A：合并前红线检查

以下任一项成立，变更不得合并：

```text
❌ 页面直接请求 API、操作数据库或调用第三方 SDK
❌ 客户端直接决定支付成功、权益或资源归属
❌ Token/密码/支付凭据明文存储或写入日志
❌ 金额使用 Float/Double 计算
❌ 空 catch、静默失败或底层异常直接展示
❌ 关键生命周期只实现 Happy Path
❌ 用全局状态承载本地或短期数据
❌ 一个 Boolean 隐藏复杂业务状态
❌ Feature 访问其他 Feature 内部实现
❌ AI 猜测契约、生成伪代码或跳过验证
❌ 未定义验收标准就宣布完成
```
