# Git 宪章

> 适用范围：仓库内所有 Git 操作，包括提交、分支、合并、重放历史、标签和发布相关操作。
>
> 优先级：本宪章高于团队习惯、局部约定和个人偏好。任何违反本宪章的 Git 行为，都视为未完成或不合规。
>
> 目标：让 Git 历史可读、可追溯、可审查、可回滚，并让每个提交都能准确表达一个变更意图。
>
> 版本：v1.1.0 ｜ 生效日期：2026-08-21 ｜ 变更记录：见 [constitution.md](../../constitution.md)「变更记录」。

## 1. 核心原则

1. 所有提交信息必须强制遵循 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。
    - 提交信息必须保持标准结构，不得使用随意命名。
    - `type`、`scope`、`!`、冒号和 `BREAKING CHANGE` 的语义必须符合规范。

2. 一个提交只表达一个清晰意图。
    - 不要把多个无关修改混进同一个提交。
    - 功能改动、测试补齐、文档更新和格式整理，若可以拆分，就尽量拆分。

3. Git 历史要服务于协作和回滚。
    - 历史应尽量清晰，便于代码审查和问题定位。
    - 任何破坏性操作都要先确认影响，再决定是否执行。

4. 共享分支上的历史默认不可重写。
    - 对已共享、已推送、已进入协作流程的分支，不得随意改写历史。
    - 需要 `rebase`、`squash` 或 `force push` 时，必须先确认不会影响他人。

5. Git 操作必须与变更范围一致。
    - 提交前先确认工作区内容，避免把无关改动一起提交。
    - 大范围改名、移动、删除或重构，应当拆分为更容易审查的步骤。

## 2. 提交规范

1. 标准格式：

```text
type(scope)!: subject
```

2. `type` 必须使用 Conventional Commits 允许的语义类型。
    - 常用类型包括：`feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`build`、`ci`、`perf`、`revert`。
    - 若团队需要新增类型，必须先约定清楚含义，再统一使用。

3. `scope` 应尽量具体。
    - `scope` 用来标识影响范围，例如 `auth`、`payment`、`ci`、`docs`。
    - 不是每个提交都必须带 `scope`，但当范围明确时应优先填写。

4. `subject` 必须简洁、具体、可读。
    - 使用祈使语气，描述这次提交做了什么。
    - 不要以句号结尾。
    - 不要写成模糊的占位词，例如 `update`、`temp`、`misc`、`fix bug`。

5. 破坏性变更必须显式标记。
    - 需要破坏性变更时，标题中使用 `!`。
    - 同时在正文或 footer 中写明 `BREAKING CHANGE:`，解释破坏点、迁移方式和兼容方案。

6. 必要时补充正文和 footer。
    - 正文用于说明背景、原因、风险、影响范围和验证方式。
    - footer 可用于关联任务、关闭事项或记录补充说明。

7. Git commit 的提交信息内容默认使用中文。
    - `subject`、正文和 footer 应使用中文准确描述变更意图。
    - Conventional Commits 固定字段、接口名、协议字段名、第三方标识等必要内容可以保留英文。

8. 提交示例：

```text
feat(auth): 增加登录失败次数限制
fix(api): 修复空参数导致的 500 错误
docs: 更新发布流程说明
refactor(cache)!: 简化缓存键结构
```

## 3. 分支与合并

1. 本地分支可以按需整理历史，已共享分支默认不允许随意重写。
2. 执行 `rebase`、`squash`、`reset` 或 `force push` 前，必须先确认影响范围。
3. 合并请求应尽量保持提交序列清晰，不要把无关改动混入同一个提交。
4. 合并策略应以可审查、可回溯为优先，不得为了图省事破坏协作历史。

## 4. 操作纪律

1. 提交前先检查当前状态和差异，确认只包含预期改动。
2. 不要把格式化噪音和业务改动硬塞进同一个提交，除非两者必须同步发生。
3. 不要在未说明原因的情况下修改公共历史、标签或发布记录。
4. 涉及跨目录移动、重命名、删除或大范围替换时，优先拆成多步提交，降低审查成本。

## 5. 验证要求

1. 与 Git 相关的流程变更，必须说明验证过什么、为什么足够。
2. 如果仓库接入提交信息检查，必须把 Conventional Commits 作为强制门禁，不得降级为建议。
3. 发现不合规提交时，优先修正提交信息或拆分提交，而不是放宽规范。
